# 颜色决策规则

Phase 1 前读取第 1、9 节，先从原稿建立显著性、业务优先级、连续表面与等价实例关系；Phase 2 生成配色提案前读取第 3.0–4 节，把表面家族、明度拓扑、彩度与受光感作为初始选色门禁；用户选定方案后、Phase 3 冻结 Paint Recipe 前再完整读取其余适用章节。本文件是颜色与视觉层级的唯一权威定义；执行文件只负责把这里形成的 Paint Recipe 写入节点，验收文件只检查是否满足。Phase 3 只能展开和加强已通过的选色目标，不能首次补做或降低这些目标。

画风迁移启用时，已登记风格载体的原材质、图片和 Paint 结构保留限制由[《画风迁移规则》](style-adaptation.md)的最小白名单覆盖；颜色角色和精确保护继续有效。

`protected-hero-controls`（KV 上的返回、规则、钱包、客服、分享等入口）同模式精确保留全部样式。跨深浅模式允许前景配色适配和有必要性证据的既有底托最小联动，唯一边界见《Figma 执行规范》第 5.4 节；几何、业务状态和素材保护优先于普通换色/画风迁移。仅登记通道进入入口专用配方，不以旧色残留为由扩大范围。

## 1. 先定显著性，再定色相

先查看原稿整页及关键区域真实灰度图，再结合业务语义建立：

- `sourceSalienceMap`：各角色相对局部背景的明度差、色度/色相差、材质高光、面积、重复频率、位置和当前视觉顺序。
- `sourceLuminanceTopology`：页面、卡片、容器、文字、Icon、Tab、小按钮和 CTA 的灰度明暗顺序与局部对比。
- `semanticPriorityMap`：全局 CTA、卡片内主要操作、次级操作、选中状态、信息、分组、表面和装饰的业务优先级。

Phase 1 只冻结上述原稿证据和 `semanticPriorityMap`。Phase 2 结合新 KV、候选 UI 模式和表面深度，为每套方案先输出不含具体 Hue 的 `targetSalienceOrder`、`roleLightnessPlan` 和 `targetLuminanceTopology`，再选颜色；不能在尚未分析新 KV 时提前冻结目标明暗。

灰度分析必须形成可复验的元素间关系，不能只有“按钮浅、CTA 最强”等角色描述。对原稿主体明暗接近的同族主要小按钮与 CTA，登记完整实例、同职责主体区域和真实宿主；新稿联合确定主体明暗范围及色彩关系。跨模式允许整个家族由亮转深或由深转亮，但不因此把家族内成员分别做成重深色和轻浅色。信息优先级与主体灰度接近分别验收，不能用 CTA 面积较大抵消配色关系失效。共同按钮锚点写入 `colorManifest.schemeAnchorContract.button`，各按钮稳定主体通道标记 `anchorId=button`；关系与合成样本进入执行工具第 4.6 节的 `button-appearance-family`。

Phase 5 在[完整局部场景](execution-workflow.md)中验证这些关系，保持背景、材质、文字、Icon 和操作的上下文完整；Phase 7 再判断扩展后的整页面积与重复频率。原稿灰度是层级依据，不是每个像素的固定亮度模板。

默认层级：当前可用的全局 CTA 是最强交互焦点；在颜色角色上冻结 `controlColorSalienceOrder=icon-container < selected-tab < primary-button`，即普通 Icon 底托最轻、选中 Tab 更明显、大小主要按钮共用最明确的操作色。CTA 与小按钮主体仍共享 `buttonPrimary`，额外强度只来自原有尺寸和材质。该顺序比较最终合成后的色彩存在感、宿主分离、面积与边界，不要求单个明度、彩度或对比度数值机械递增。关键数据与功能 Icon 图形可成为次级焦点，但不能系统性压过主要操作；禁用态、次级操作和明确业务例外按真实语义处理。

不能只比较单个节点。大面积或高频重复的非操作元素具有 `areaWeightedSalience`，即使单个对比不高，也可能累计压过按钮。灰度、模糊和缩略图必须用于识别这种问题。

原稿 Hue 不作为新方案的取色依据；原稿提供结构、角色、灰度骨架、面积、频率和材质层职责。媒体覆盖层、`protected-rank-top3` 及 `protected-marketing-banner` 的原色按保护规则保留，不用于反推新主题色板。跨深浅模式可以转换亮暗方向，但显著性顺序必须保留或有业务纠正理由。

## 2. 从 KV 来源色生成规定的完整方案

候选数量、方案 ID、交互方向和用户确认门禁统一按[《配色方案提案》](palette-proposal.md)执行。无可靠金属证据时，深色/混合新 KV 默认给出深/浅 UI × 同色系/撞色 4 套，浅色新 KV 给出浅色 UI × 同色系/撞色 2 套。有可靠金属证据时，每个适用 UI 模式改为同色系金属、正常明亮金色、干净深色三套，因此深色/混合新 KV 默认 6 套，浅色新 KV默认 3 套。用户明确限制目标 UI 模式或交互方向时只保留符合要求的方案。方案数量来自本 Skill 的默认交付契约，不得因“证据充分”擅自缩减；缺少生成某类方案的必要基准时按输入阻塞处理，不能伪造、静默缩减或提交无效候选。

每套都先由 3–5 个有空间角色的新 KV 来源色建立关系色板，再展开到页面、卡片、交互与文字；不能直接选择一个 `accentColor` 后逐控件临时派生。可靠金属证据触发三案矩阵：`metallic-analogous` 从实际金属稳定本色、中间调、暗部与高光建立同色系金属按钮；`gold-bright` 建立正常明亮金色按钮；`clean-deep` 从有来源的深色主体、标题、金属暗部或稳定环境深端建立干净深色按钮。正常金色的主体中间调必须明亮、有彩且明确为金黄，不能用暗铜、棕橙、土黄或低明度黄褐替代。无可靠金属证据时使用 `analogous|contrast`；撞色先用稳定表面家族生成约 180° 对向候选，再与 KV 中有来源、面积/重复证据的高彩高明度色比较，记录 `contrastDerivation=hue-opposition|kv-vivid-accent`；同一 Hue 的深浅变化不得标为撞色。页面/卡片仍来自稳定环境色，Tab 默认继续引用表面同系色。方案确认前不写 Figma。

Phase 2 的每套提案内部必须保存完整角色方向、来源和门禁；面向用户只投影六个冻结锚点：

```text
background / card / number / icon / button / tab
```

内部仍须包含 `buttonVariant / hueStrategy / materialStrategy / surfaceFamilyPlan / accentFamilyPlan / contrastDerivation / surfaceContrastBasis / metalAccentEvidence / buttonToneDirection / cardSurfaceStrategy / iconPairPlan / targetLuminanceTopology / targetSalienceOrder / colorClarityPlan.lightnessAndChroma / proposalColorPreflight`；不适用的分支字段明确记为 `null`，不能省略推导方式。六个锚点是用户选择所需的代表性关系，不是逐 Paint Recipe，也不表示六种强调色。用户选定后将其冻结为 `schemeAnchorContract`，Phase 3 才展开文字 Alpha 阶梯、Icon 底托、按钮材质、卡片氛围和节点级目标；所有派生配方必须引用该契约，不能在执行中静默换成另一套家族。

AI 以整套页面关系评估，有多个候选时成对比较：KV 协调、大面积舒适度、表面层级、交互显著性、材质一致性、冷暖/彩度/明度平衡、旧主题继承风险，以及是否出现不合时宜的浑浊、灰化、暗沉或抢焦点。保留最终方案、逐角色理由和实际考虑的其他方案淘汰理由。“廉价、糖果化、霓虹化、过艳”等评价必须落到可见问题，例如无光照依据的多色扩散、亮边吞没主体、大面积彩色块压过操作；不能仅因颜色鲜亮、带邻近色过渡或具有强高光就先行淘汰。

候选须有合理的彩度和明度设计，不能用某色相的一套过淡或过暗方案代表整个色相家族。先定位问题属于色相、明度、彩度、光照组织还是背景关系，再针对该维度试色；不能因一个组合失败就排除整个色相家族，或认定必须更换色相。某一文字色或高光组合不合格，只淘汰该组合。未经渲染的候选顾虑标为待验证，不能写成已经观察到的缺陷；具体试色修正放在 Phase 5。

Hue、聚类面积和对比度只作为证据，不能自动选出审美胜者。真实视觉失败可否决方案；对应对比度按《验收规则》第 5.1 节分模式执行：同深浅且无画风迁移时不低于原稿，深浅转换或画风迁移按真实上下文确定。WCAG 固定比值仅在用户明确要求时启用。禁止建立“题材、行业或人群标签 → 固定 Hue”的查色表；用户在当前任务明确提供的配色偏好可以作为决策起点，仍须结合本次 KV 与整体 UI 验证，不机械套固定色值。

## 3. 受控色板

默认关系：

```text
大面积表面：environmentColors / uiContinuationPalette 及其邻近中性色
交互：interactionPalette
局部材质：materialMidtones / specularColors / highlightOnlyColors
文字：按 UI 深浅分流的 textBaseColor；浅色 UI 使用低 B 深中性，深色 UI 使用 B=100 浅中性
语义状态：真实成功、警告、错误、危险色
```

页面、卡片、大面积内容容器及其普通描边围绕同一环境家族建立连续表面系统，普通文字按第 6 节处理；按钮、CTA、选中状态和标签独立决定操作力度，色相关系服从下文第 3.0 节的默认相近家族与撞色例外。局部 Icon 容器/底托仍按第 7.1 节独立配色，并验证与整体家族的承托关系。不要把所有角色做成同一个 RGB、明度或渐变。

### 3.0 颜色来源与表面家族

把 KV 的 `colorAnchors` 映射到现有角色配方：Phase 2 在每个 `themeDecision.paletteProposal` 候选内登记 `surfaceFamilyPlan`，包含页面/卡片/内部容器/普通边界的家族与锚点引用、目标明暗关系，以及实际存在的环境光和反射职责；用户选定后，Phase 3 将该计划提升为最终 `themeDecision.surfaceFamilyPlan`，不重新选另一家族。无金属候选在 `hueRelationshipPlan` 内登记 `strategy=analogous|contrast`；金属候选登记 `buttonVariant=metallic-analogous|gold-bright|clean-deep`，并记录实际金属证据、金色质量目标或深色来源。无金属撞色记录 `contrastDerivation=hue-opposition|kv-vivid-accent`、对向基线候选、KV 鲜明候选及最终取舍证据。所有候选记录 `surfaceContrastBasis`、`kvPrimaryHue`、实际考虑的候选、`buttonToneDirection=bright|clean-deep`、最终候选、主辅色面积分工及真实彩色验收方法；未使用的分支字段明确记为 `null`。其他角色在自己的 Recipe 中引用来源锚点或明确的用户配色要求。原稿的 `sourceColorRelations` 解决同色复用；此计划解决 KV 与新 UI 的环境延续，二者不能互相代替。

- **先判环境能否延展，再比较颜色。** 页面主锚点优先来自大面积、连续、空间稳定且延展后自然的环境场；局部人物、建筑、树叶、标题、Logo、镜面反光或孤立前景色即使像素鲜明也不获得同等权重。底部区域只有在最终 Hero 中实际可见，并同时具有横向连续、面积充足、颜色稳定/较纯、环境身份明确和低具体纹理风险时，才可因接缝优势提升为主表面候选；如连续草原、海面、天空或雾光。被裁掉的源图底部、局部暗边和前景物不参与该加权。无法直接判定时按同一明度/彩度力度做页面面积预览，不凭题材名称决定。
- **底部延伸是情境候选，不是自动锁色。** 建立 `heroBottomExtensionDecision`：先判断最终可见下缘是否由大范围环境场构成。杂乱、具体纹理、人物/建筑/树叶/阴影/装饰等局部前景主导时设为 `not-suitable`，页面锚点回到整张 KV 的连续环境色；大片草原、海面、天空、雾光、较纯颜色或低纹理渐变时设为 `eligible`，再与其他环境候选按空间合理性、整页面积效果、表面层级和舒适度比较。最终可为 `selected-solid|selected-gradient|eligible-not-selected|not-suitable|existing-transition`。选择延伸时接缝起点匹配实际下缘，并按原空间趋势继续；未选择时保存更优环境依据与可验证衔接方式。不能只因底部位置或单行纯色强制采用，也不能在适合延伸时无理由忽略明显接缝优势。
- **表面同家族，交互单独定关系。** 页面背景、卡片、内部容器及普通边界来自同一环境家族；按钮/CTA 再按同色系或撞色策略引用环境、主体或材质锚点，不因“默认相近”被强制与页面同色。按钮可以比背景更亮或拥有更高彩度，以既有材质与轮廓形成操作焦点；色相相近不等于同 Hex、同明度或弱化按钮。不能为区分卡片逐张选另一家族，也不能把多色 KV 的每种自然景物颜色各分配给一个大面积 UI 角色。
- **浅色 UI 使用有彩页面、低彩近白/纯白卡片和清楚操作。** `targetUiMode=light` 时，页面基底必须具有较高感知明度并保留足够有效彩度，使主题色清楚但不沉重；不得把页面推成近白、灰白或低彩雾色。撞色方案须为卡片冻结 `cardSurfaceStrategy=tinted-near-white|pure-white-atmosphere`：先降低 HSB 的 S、提高明度，让大面积卡片明显比页面更接近白色；KV/页面彩度较强、卡片面积或重复较大时允许 S=0 的纯白稳定底，只在原有卡顶氛围、包边、角饰或光带中保留淡主题色。不能为了证明“来自 KV”强行给白卡叠一层显脏的高彩底色。纯白方案仍须靠页面差异、既有边界/阴影或顶部氛围清楚分卡；没有原卡顶氛围时不新增装饰。内部容器在同家族内形成介于页面与卡片之间或同样清楚的层级。主要按钮与 CTA 先比较明亮高彩方向；当 KV 与页面整体偏浅时，默认使用来自 KV 主体、标题或金属证据的干净深色方向，只有真实宿主证明明亮按钮仍能形成清楚焦点时才保留明亮方向。干净深色必须保留清楚色相、有效彩度和合理受光，不能灰闷、近黑或只靠少量亮边。功能 Icon 图形按真实底托保持清楚，底托遵守第 7.1 节“淡淡带色、不暗沉”。普通文字、描边和精确保护项不适用“全部提亮增艳”。
- **交互强调集中在按钮与突出高亮。** 有可靠金属证据时按三案矩阵分别验证：同色系金属忠实承接本次金属家族；正常明亮金色保持清楚金黄色相、较高感知明度、有效彩度和足够受光面积，不得落成暗铜/棕橙/土黄；干净深色有可追溯来源且不灰黑暗沉。无可靠金属证据时，`contrast` 优先评估 `hue-opposition`，再比较 KV 中更高彩、更明亮且有主题证据的 `kv-vivid-accent`；若后者在真实宿主上更突出，可作为撞色，但不能伪称 180° 补色。两者均须与同色系方案清楚分离，不能只改深浅。页面、卡片和容器继续使用稳定环境家族；主要小按钮与 CTA 共用单一 `buttonPrimary`。Tab 选中态默认使用表面家族或邻近色，不跟随按钮方向改变；只有用户明确要求或强业务语义证据时才例外。大面积表面若分属无连续环境依据的色相/冷暖家族即为 FAIL；不能把按钮强调扩散为整页第二主底色。
- **强调家族节制，而非统一材质。** `accentFamilyPlan` 对 `number/icon/button` 的稳定主体逐个登记家族 ID、KV 来源、可见面积/频率。普通 Icon 固定 `iconSource=surface-environment`：从背景/卡片的连续环境色提取色相，按真实底托派生可见的明度和彩度，不直接取孤立高光，也不由按钮或数字反向决定 Icon 色。深色 UI 固定 `darkNumberSync=icon`，高亮数字的公开 `number` 与 Icon 稳定主体的公开 `icon` 锚点必须完全同 Hex/RGB；这是代表色一致，不要求把 Icon 的金属暗端、镜面反射和高光刷成单色。按钮可以成为第二个高彩家族。浅色 UI 的数字按实际宿主选择，但数字/Icon/按钮默认仍最多形成两个显著高彩家族；若有主题级 KV 面积/重复、业务语义或用户明确偏好，才可事先登记第三家族例外并用面积预览验证。表面/Tab 的低强调同系变化不算新强调族，孤立青蓝镜面亮点也不能提升为整组 Icon 的第三主体色。此约束不固定所有新 KV 用紫/蓝。
- **来源与用途对应。** 稳定环境支持大面积底色和 Icon 稳定主体的色相来源；有空间证据的弥散环境光支持卡片受光；主体、材质与强调方向支持按钮及局部反射。深色 UI 的高亮数字与 Icon 共用代表色。允许真实的有色环境光影响卡片，但不得把镜面亮边或局部主体颜色当作普遍环境光。材质名称不决定色相，原稿材质色也不作为新锚点。
- **调整深浅仍保留颜色倾向。** 跨模式不必照抄锚点 RGB，也不强制保留每个 HSV H 数值；新明度下仍应延续有证据的冷暖与色相家族。暗底和浅底都要防止中性色化、黄化或其他无依据的漂移。接近中性时以真实 RGB/冷暖和视觉关系为主，不用不稳定的 H 判失败。Icon/按钮按第 3.2 节联合选择 H/S/V，不直接复用表面色；透明度、结构和保护约束不因家族计划解除。
- **验合成色，不能只验底色。** 把底色、渐变、纹理、反射、描边、祖先 Alpha 和下层背景一起看。底色取对但叠层使大面积表面偏向其他家族，也属于一致性失败。沿实际绘制顺序定位贡献层，优先修正其取色；强度只在原有允许范围内调整，不一律降饱和、压暗或新增罩染。
- **色相关系不确定时做可比对照。** 在同一代表场景里比较有来源依据的家族，尽量保持明暗层级、彩度力度、字色与材质结构可比，观察 KV 衔接及表面整体倾向。只试按钮 V、字色或高光强度不能解决表面 H 的不确定性。没有疑点且来源/渲染证据充分时不增加无意义候选。
- **一致性覆盖所有角色的关系。** 环境表面协调不代表 Icon/按钮色相就合适；各角色独立决定明度、彩度与材质，同时服从已登记的整页色相关系。同族实例共享最终配方，不能因来源组件或节点类型不同各自偏色。品牌、内容媒体、精确保护色及有业务依据的语义色保留各自职责，不强制并入主题家族；它们不授权拆分背景、卡片与主要操作的家族。

Phase 5/7 形成 `themeColorConsistencyAudit`：KV 原始环境区域与实际 UI 表面并排检查，分别判断稳定区和受光区，再看整页重复面积。对比度、彩度、明度、旧色清理或配方执行正确，都不能单独使这一项 PASS。不设跨所有 KV 的固定 Hue 差阈值或统一合格色板，具体检查按《验收规则》第 6 节。

高明度、高彩度颜色大面积使用前必须执行面积放大审查。仅在实际面积、重复频率、舒适度或层级出现问题时调整彩度、明度或表面关系；任何具体 Hue 都不触发自动增减彩度。普通正文优先协调且可读的中性方向，深浅由真实背景决定。任一有来源依据的色相都可进入按钮、标签和数据候选，按整套方案验证。

“协调、克制、高级”不能自动转换成降低所有角色的饱和度。大面积表面可以柔和，主要操作仍须形成明确焦点；小面积按钮具有更高彩度不等于过艳。不要把页面、卡片、Icon、标签与按钮全部收成相近的浅灰/粉彩后，仅靠深色文字维持层级。深色 UI 或明确中性方向可在真实背景上用较低彩度配合明暗、轮廓和材质建立层级；`targetUiMode=light` 时，近白卡片可以低彩，但有彩页面基底和主要操作不能以低彩度方案通过。规则不设跨色相固定数值；若 KV 没有可靠有彩锚点，不发明无关高彩色，而是按输入阻塞取得用户强调基准或降低色相结论可信度。

### 3.1 必须达到的饱和度、对比度与清晰度

目标是主动建立好看且清晰可辨的页面，不能只证明“没有过艳”或“没有明显发灰”。在 `themeDecision.colorClarityPlan` 中逐角色确定并在实际渲染中满足以下要求：

- **彩度充足且分配合理。** 对有鲜明色彩的 KV，UI 必须保留有力度的主题表达；主要按钮的有效彩度须足以承担操作焦点，不能只让 Hero 鲜明而把 UI 所有角色都洗成灰白。相近色相、相近明度下，主要操作应比弱标签、图标容器和背景拥有明确的彩度区分。其他配色可结合明度、色相与轮廓建立同等清楚的焦点，但仍须解释其彩度如何匹配 KV 和操作角色。
- **表面层次明确。** 页面、卡片、内部容器在实际尺寸下各自可辨，合成后的表面对比按《验收规则》第 5.1 节执行适用策略；不能依靠内容文字的位置去猜测卡片范围，也不能让不同层次都混成近似底色。
- **操作突出且状态可辨。** 不阅读按钮文案也能识别主要操作区域；普通 Icon 底托、选中 Tab、主要按钮/CTA 的颜色显著性依次增强，小按钮强于邻近 Tab，全局 CTA 是最强交互焦点。已有启用、禁用、选中与未选中状态分别可辨，不能都依靠很小的透明度差异。
- **文字与图形清楚。** 需换肤文字达到第 6/8 节与《验收规则》的对比度要求；功能图形与容器清楚分离，不能以字色更深替代整个按钮的显著性。媒体和前三名保护色按原稿保留，不为达标重着色。
- **整页美观协调。** 彩度和对比集中在合理角色，强弱有节奏，材质基底、反射、高光各自成立。不能为了“保证饱和度”把所有元素一起增艳，也不能用刺眼描边或大片泛白高光替代有效的角色对比。

检查时对照新 KV 的稳定色与材质中间调，采样最终合成后按钮主体、局部背景和邻近弱控件的代表区域；区分主体色面积与少量高光，不能用最鲜艳的一个像素代表整个按钮。需要量化时采用一致的色彩空间记录明度/彩度，同色系可用一致的饱和度指标辅助判断；不同色相的相同 HSV 饱和度不保证相同视觉力度，不能据此自动通过。文字对比度仍用规定公式单独计算。

彩色 1:1 图检查真实彩度、细节和状态，灰度检查明暗层次，模糊与缩略图检查焦点和面积分配。各项均须给出具体节点/截图证据；任何一项不满足即回到配色或合成层修正。明确的中性/低彩度 KV 可使用低彩度 UI，但仍必须达成清晰层级、操作焦点和可读性；不要添加与 KV 无关的鲜艳颜色来凑数值。

### 3.2 分开判断彩度、明度与受光感

“饱满”不是独立指标，也不能作为验收结论。描述颜色时至少说明：色相倾向、彩度是否充足、主体感知明度、光照与面积关系。高饱和颜色仍可能明度偏低，较高明度的颜色也可以保有鲜明彩度；是否合适由 KV、组件角色与背景共同决定。HSV 的 S 只描述该空间的饱和度，V 也不等于感知明度。需要量化时使用一致的感知色彩空间（例如 OKLCH 的 L/C）辅助比较，不能用单一 S/V 或最亮像素证明好看。

在 `colorClarityPlan.lightnessAndChroma` 中记录：

- **KV 的光照气质与角色目标。** 分开描述环境的明亮/深暗程度、主体本色及受光方式，以及整体色彩力度是淡雅、鲜明还是混合；明亮不等于淡色。记录目标 UI 模式、实际宿主及按钮/CTA/Icon 的来源锚点。`targetUiMode=light` 时主要按钮与 CTA 先比较鲜亮方向；当 KV 与页面整体偏浅时，默认优先比较有主体/标题/金属证据的干净深色方向并登记 `buttonToneDirection=clean-deep`，只有它在实际宿主上比鲜亮方向形成更清楚操作分离时才选用。`targetUiMode=dark` 的普通鲜亮按钮仍以 B=100 为基线；只有可靠金属主体/金属深端允许降低 B。页面承接环境，控件承接适合其角色的颜色与材质；可以采用文字同色系，但不能让标题、Icon、按钮全部复制正文 RGB、透明度和视觉权重。
- **主体面积的真实明度。** 检查最终合成中的主体中间调、暗部占比、局部反射和高光覆盖范围。少量亮边不能掩盖大部分表面偏暗，最鲜艳像素也不能掩盖主体发灰。
- **按问题维度对照试色。** 分别验证色相、明度、彩度、材质和背景关系，不得仅凭某一维度达标认定整体方案合适。Phase 5 若发现未满足目标或仍有关键不确定的维度，在同一代表白名单上对照试色；尽量保持其他条件可比，必要时联合调整文字和背景，并记录变量及截图。调整方向由证据决定，不预设更换色相。`targetUiMode=light` 的页面表面仍须满足明亮有彩方向；主要按钮/CTA 则比较 `bright` 与有来源依据的 `clean-deep`，以真实宿主上的操作分离、彩度、受光和整页重量决定，不能把无证据的压暗当成对比方案。不同 Hue 的候选不能替代对明度/彩度/材质问题的验证。已具有充分视觉证据的方案不为凑固定方向或数量增加试色。
- **受光感是否仍成立。** 基底应保有自身颜色，反射能表达环境色，高光能标明受光面，暗部用于塑形。对明亮 KV，不能把稳定中间调理解为最深材质色，也不能用压暗整个基底来制造层次。

数字满足只代表相应指标满足。若彩度和文字对比度合格，但合成结果在视觉重量、材质或操作层级上不符合已记录的目标，仍为失败；过暗、过亮、发灰或彩度过强都须结合实际背景和角色判断。不得为所有 KV、所有角色制定同一套万能阈值，也不要将一次成功或失败的具体颜色变成后续固定配方；但功能 Icon 图形与启用态主要按钮须执行下述按 UI 模式、按钮尺寸和主体职责分类的 Figma HSB 选色护栏。

#### 3.2.1 Figma HSB：按 UI 模式 × 按钮尺寸分四类

本节使用 Figma 色板中的 `H/S/B` 口径；其中 `B` 等同 HSV 的 `V`，不是感知亮度。四类固定为 `dark-ui-small-button / dark-ui-large-button / light-ui-small-button / light-ui-large-button`：`dark/light` 指页面 UI 模式，`small/large` 指业务尺寸。不得再把按钮自身看起来较浅或较深当成四类，也不得新增“金属、渐变、柔光、立体”类别。按钮自身方向另以 `buttonToneDirection=bright|metallic|clean-deep` 记录。

渐变先拆成 `brightStop / dominantMidtone / stableDarkStop / edgeOrDepth / highlight / transparentFade / tinyShadow`。主体范围只统计真实承载按钮本色并占有可见面积的亮端、中间调与稳定暗端；白色镜面高光、透明端点、结构蒙版、极小阴影不计入主体 B 门禁。包边和立体深度层必须单列，但不得冒充主体或把主体压暗的责任藏到“阴影”里。

本轮参考重新归纳后的核心结论是：**普通鲜亮彩色按钮的主体本色色标以 `B=100` 为默认值，而不是 `B75–100` 或 `B80–100` 的宽范围。** 只要一个色标承担可见面积的本色/中间调，即使它处于渐变较暗一端，也不应仅因为“渐变需要层次”就把 B 降到 77、83、91 或 96。用户已指定的暖亮金示例中 `#F9DB92` 约为 `B98`，因此 `gold-bright` 可在有该金色方向证据时使用 `B98–100` 的近满明度色标；这只是亮金容差，不是低 B 深色例外。层次优先用 S、邻近 Hue、局部高光、包边和小面积塑形暗部表达。

除上述 `gold-bright B98–100` 近满明度容差外，允许主体色标明显低于 100 的默认例外只有两类，且都需要明确证据：

1. `targetUiMode=dark` 且按钮有可靠金属证据：同色系金属主体，或明确从该金属稳定暗部派生的深端方向，可低于 100 以建立镜面明暗分段；须证明亮部面积、反射和轮廓在深色宿主上仍清楚，不能变成暗铜、灰黑或只剩窄亮边。非金属深色不能借此降 B。
2. `targetUiMode=light` 且按钮为已选择的 `clean-deep` 方向：主体可低于 100，以在浅页面上形成明确操作分离；参考 `#BE9D72→#966F3F` 约为 `S40/B75 → S58/B59`。这只是深色方向校准，不授权所有浅色 UI 按钮降 B，也不固定使用棕色。

四类分别执行相同的主体门禁，但必须分开总结，不能互相覆盖：

| 按钮类别 | 普通鲜亮/亮金主体 | 允许的低 B 例外 |
|---|---|---|
| `dark-ui-small-button` | 所有可见主体本色色标 `B=100`；亮金可 `B98–100` | 仅可靠金属主体/金属深端；需真实小尺寸验证 |
| `dark-ui-large-button` | 所有可见主体本色色标 `B=100`；亮金可 `B98–100` | 仅可靠金属主体/金属深端；分别记录金属亮端/中间调/暗端 |
| `light-ui-small-button` | 所有可见主体本色色标 `B=100`；亮金可 `B98–100` | 仅已选 `clean-deep`；需真实小尺寸验证，不能直接照搬 CTA 暗端 |
| `light-ui-large-button` | 所有可见主体本色色标 `B=100`；亮金可 `B98–100` | 仅已选 `clean-deep`；参考深色主体关系仍须结合当前 KV 与宿主验证 |

S 不设跨色相万能下限。低彩蓝紫、暖亮金和高彩橙红在 `B=100` 时可以具有不同 S；需要的是清楚色相、足够有效彩度和真实宿主分离。`gold-bright` 的主体仍应处于暖亮金方向并使用深棕字，不能借“金属”例外降低 B 变成暗金；普通非金属按钮也不能借材质名降 B。

对每套方案分别记录 `colorClarityPlan.hsbGuardrails.darkUiSmallButtonSummary / darkUiLargeButtonSummary / lightUiSmallButtonSummary / lightUiLargeButtonSummary`。只填写当前目标 UI 模式下的两个尺寸，另两类带证据记 `not-applicable`。每个适用 Summary 列出代表节点、`buttonToneDirection`、亮端、主体中间调、稳定暗端、包边/深度层、面积职责、排除项、是否命中 `B=100` 主体门禁、亮金近满明度容差或哪一条低 B 例外，以及 PASS/FAIL；随后再记录 `buttonFamilyConsistency`。小按钮与大按钮必须分别通过。

普通功能 Icon 图形独立于按钮门禁执行，但必须和底托成组决策。它可从背景/卡片的同色系派生更鲜明的图形色，也可在有层级证据时与按钮同色。普通鲜亮 Icon 的稳定主体色标可优先使用 `B=100`；`B=100` 本身不构成过亮，须结合色标职责、真实卡片、底托、图形面积和重复频率判断。若原可见渐变以低 S/高 B 到高 S/高 B 建立层次，目标必须逐色标保留可感知的 S/颜色差；不能因为两端都高明度就映射成同一个 RGB。与背景同色系时重点保持 Hue/冷暖连续，并通过色标差异、边界和底托拉开，不复制背景 RGB。Icon 规则不得反向推导按钮范围。

Icon 底托按图形↔底托↔卡片的成组关系选择。浅色 UI 中底托应比近白/纯白卡片多一层很淡的颜色，通常进一步降低 S、提高 B，避免形成暗底；图形的层次主要由原有渐变色标之间的饱和度/明度关系表达，不能用单一荧光纯色替代整条渐变。深色 UI 以相对宿主的局部抬升或有依据的色相/彩度/边界承托图形。所有判断都看最终合成，不机械套绝对 S/B。

护栏是 Phase 2 的候选淘汰门槛和 Phase 7 的诊断门禁，不是自动审美通过证。低于对应“尺寸角色＋方向”的下限时，除非有预先登记的角色特例、来源依据与真实渲染证据，否则直接 `FAIL` 并重选；达到范围后仍须验证感知明度/彩度、各色标面积、渐变过渡、材质受光、真实宿主分离与整页层级。不同 Hue 即使 HSB 相同也可能呈现不同视觉力度。禁用/次级控件、普通文字、页面/卡片表面、受保护媒体、图片 Icon、Logo，以及仅承担高光/小阴影/结构的色标不适用本表。

不要要求 `按钮 B > Icon B`，也不要因为 Icon 主体达到 `B=100` 就判它过亮或压低按钮。普通鲜亮大小按钮的主体本色色标仍执行 `B=100`；只有上述深色 UI 金属或浅色 UI `clean-deep` 例外允许低 B。Icon 按成组关系选择色标配方；原渐变各端须保持可感知差异，并在整页重复中弱于主要操作。`Icon 底托 < 选中 Tab < 主要按钮/CTA` 继续按尺寸角色、主体 HSB、实际面积、真实宿主分离、边界与重复频率综合判断，不能把这一视觉顺序翻译成单一 B 值递增。

**核心目标：按钮、CTA 和功能 Icon 在实际背景上突出，不能暗沉。** 以原稿理解信息优先级和材质分工，以新 KV 与真实宿主决定颜色；不沿用失败版本作基准。满足下面条件时先建立浅→浅比较基线，其余情况直接联合选择 H/S/V，不要求深→浅一律提亮、浅→深一律压暗。当前任务另有明确通道锁定时登记执行，不把比较基线误作其他模式的限制。

**浅→浅且新背景不太淡：可把保留原 S/V、仅调整 H 作为诊断对照，不作为最终门禁豁免。** 当 `sourceUiMode=light`、`targetUiMode=light`，且按钮/Icon 的实际页面或卡片宿主不是很淡的低差异背景时，可先让按钮、CTA 与 Icon 图形逐渐变色标保留原稿 S、V 和 Alpha，仅按新 KV 调整 H，用于检查原稿的明快感与材质层次能否迁移。若普通鲜亮按钮的可见主体本色色标不是 `B=100`，该对照只能用于诊断，最终候选仍须调整到第 3.2.1 节门禁；不得用“保留原 V”放行 B77/83/91/96。背景是否过淡由完整局部场景判断，不设万能 Hex、S/V 或亮度阈值；局部底托也不能独自代表整页背景。此基线不是通道锁定，须在提案展示前联合调整必要的 H/S/V，并记录理由。

基线仍须验证真实结果：跨色相相同 S/V 不保证相同感知明度。如果违反适用的对比度策略、暗沉、主体不突出或材质丢失，立即判该基线失败；先检查色相方向、叠层贡献与背景关系，再在允许范围内调整必要的 S/V。不能为了数值保持而放行暗沉版本。明确的任务级通道锁定冲突另按结构/保护冲突规则处理。

下表是结合 KV 的初始方向，最终按实际宿主和整页层级验证，不是四套固定色板。KV 明暗与色彩力度分别判断，混合 KV 保留环境和主体差异，不能仅凭最亮或最艳像素分类。

| 目标 UI 与 KV 情况 | 按钮 / CTA / Icon 图形的初始方向 | 必须验证 |
|---|---|---|
| 深色 UI，KV 明亮 | 可选更明亮、有主题色彩的主体与受光面 | 明亮主体有足够面积，操作突出且与 KV 协调 |
| 深色 UI，KV 深暗 | 普通鲜亮操作仍以 `B=100` 为基线；只有可靠金属主体/金属深端可降低 B | 金属暗端仍与真实背景拉开差异并保留清楚受光；非金属按钮不能以“深色风格”压低 B |
| 浅色 UI，KV/页面整体淡雅或与按钮候选近色 | 默认使用同一 KV 主体/标题/金属证据家族中的干净深色主体，并保留明亮方向作对照 | 例如淡黄背景配深棕；只有明亮方向在真实宿主上仍清楚突出时才保留，深色须有色相、彩度和受光，不得灰闷近黑 |
| 浅色 UI，KV 有鲜明彩色，且基线不适用或未通过 | 使用有 KV 依据的明亮高彩主体 | 主体保有色彩力度与操作焦点，不因浅色模式洗成粉灰或被暗部压沉 |

- **深色要干净，亮色要鲜明。** 不机械把任一鲜亮色同时压低 S/B 得到灰闷暗块。浅色 UI 的页面主题基底保持明亮有彩；其主要按钮/CTA 在 KV 与实际宿主整体偏浅且有 KV 主体、标题或金属证据时，默认登记 `clean-deep`，只有明亮方向仍能清楚突出时才保留 `bright`。这种深色仍是有彩、受光清楚的操作主体，不是低彩灰黑。普通文字、描边、阴影和次级状态按各自角色判断；禁用态沿用正常按钮配方后整体 50% 透明。第 3.2.1 节是按 UI 模式与尺寸分类的主体色标护栏，不得扩展成所有色标或所有角色的万能门槛。
- **材质分工保留，色值按证据决定。** 除明确锁定项外，不锁定原 S/V；浅→浅基线只有在视觉门禁通过时才沿用其数值。对允许换肤的 Fill、Stroke、颜色 Effect 和渐变色标登记目标颜色，默认保留颜色/Paint/节点/祖先 Alpha、混合模式、蒙版和渐变几何；已允许的 Alpha 例外仍按对应规则执行。高光、主体、塑形暗部保持可感知差异，避免色标截断或合并。无彩通道按实际职责处理：结构蒙版、精确保护和明确锁定项保持；可换肤主体可采用有来源的有色配方，高光不自动染成主体色。
- **图形和底托分别配色。** 普通辅助容器/底托按第 7.1 节独立选色，不能把父级 Icon 的整树写成同一角色或同一色值。底托弱于图形，既验证图形/底托，也验证底托/卡片；不能用浅卡片上的浅底托加浅图形制造低差异组合。
- **按计划校验，按画面验收。** 记录源色标职责、目标 RGB/HSV、来源锚点、浅→浅基线的适用性及必要调整理由，读回核对目标值、须保留的通道和允许差异。原稿与新稿同尺寸、各自真实背景对照；有失败或关键疑点时只对受影响维度作对照试色，仅适用的浅→浅场景从只换 H 的基线开始，不强制所有模式生成该基线。通道数值正确不等于视觉通过。
- **突出有层级。** 当前可用的全局 CTA 是最强操作焦点，小按钮在卡片内强于普通 Tab、类别栏、弱标签、底托和装饰；功能 Icon 清楚鲜明，但不能系统性压过主要操作。突出须在整个主体面积上成立，不能仅靠可读的文字、控件尺寸或一条亮边证明。按钮文字与主体联合选择；数字按第 6.1 节独立判断，不机械跟随按钮亮暗。

**暗沉的诊断与修正。** 已出现过深时，先区分主体感知明度偏低、彩度不足、受光面被染暗，以及 Alpha/混合/叠层压暗，记录实际主体面积与原稿材质职责。高 S 不能抵消低 B/感知亮度；少量亮边不能证明主体有质感。优先恢复有 KV 依据的主体中间调和受光面的明暗差异，再联合比较浅字/深字与局部背景，不把高光和反射统一映射成主体暗色。低 B 主体只用于深色 UI 的可靠金属主体/金属深端、已登记的非主要操作，或浅色 UI 中经真实宿主比较后成立的 `buttonToneDirection=clean-deep` 主要按钮/CTA；后者必须有主体、标题或金属证据，并在偏浅页面上比明亮方向形成更清楚的操作分离。功能 Icon 图形与底托另按第 7 节处理。任何模式都不得为了比值将主体推向近黑、把明亮 KV 的过渡压成黑带，或增加底部渐变强度造成接缝。可读性已成立时不继续为追求更高比值压暗；实际灰闷、失去色相或受光时先否决配方并重试，既有几何和保护边界保持。此项可独立否决数值通过的方案；第 3.2.1 节主体门禁只负责拦截明显不合格配方，不能替代跨主题的感知判断。

色盘下方彩虹横条调整 H；上方方块向上提高 V、向右提高 S。面板选点可根据目标调整，固定坐标不是配色或验收规则；HSV 的 V 不等于感知明度。

### 3.3 用户授权的设计师参考研究

仅在用户明确要求时读取设计师参考；默认盲测隔离继续有效。把研究写入 `colorClarityPlan.referenceStudy`，并完成以下步骤：

1. 确认用户选中节点与所属页面，只研究授权范围。模块不同仍可按小按钮、CTA、Icon 图形/底托、背景/卡片等同角色对照，不照搬布局和业务内容。
2. 同时读取实际截图和节点材质：有效 Paint、渐变色标及空间分布、Alpha、混合模式、祖先影响、可见 Effect。排除隐藏备选层；布尔子图形的 Fill 不一定独立参与最终着色，不能误作可见表面颜色。
3. 区分可编辑矢量、渐变与 IMAGE 素材。图片中的立体光影只能作为视觉目标，不能宣称几个 Paint 色值即可复现；不得擅自替换目标图片 Icon 或增加几何来追求参考效果。
4. 写清“观察到的关系 → 视觉作用 → 在目标既有结构内如何迁移”。例如同一家族中，小按钮用清楚的邻近色过渡，CTA 用更丰富的局部色光；这说明复杂度分级，不构成所有 KV 采用相同颜色的模板。
5. 对照实际尺寸、邻近背景、主体颜色面积、文字与材质。大小不同不能仅比较整块视觉冲击；区分颜色、几何、排版和素材分别贡献了什么。
6. 将值得学习的视觉关系与未验证/不达标之处分开记录。设计师参考的白字或 Alpha 不自动满足本 Skill 的对比度与结构规则。遇到既有渐变几何无法承载的空间效果，记录迁移限制，在允许范围内选择最佳方案，不越界新增材质层，也不声称已完整复刻。

## 4. 表面系统与连续深度

**同族卡片的基础表面关系。** 先区分稳定底色与叠加光影。原稿中基础底色相同或接近的收益卡、任务卡、作品卡，优先共用新基础表面配方，延续原来的接近关系；区分主要来自已有渐变、反射、高光、弱描边与氛围强度，不因“收益重要”或旧文字比值高而单独做成深色卡。强调收益优先调整数字/文字与合法光影，联合验证真实可读性。源稿确有独立表面家族或用户明确要求时才建立变体，不给所有卡固定同一 Hex，也不设置通用色差阈值。将基础表面的共同配方登记到 sourceColorRelations，整页比较同时核对稳定区和受光区，不能用局部材质氛围掩盖基础表面已被拆成无依据的多个家族。

页面、卡片和容器明度必须服从 `targetSurfaceDepth`，而不是二元模式套固定浅白或近黑。

浅色方向：页面与卡片中高区分，卡片与内层容器中等区分，按钮与表面高区分；避免三层都接近白色。

深色方向：页面与卡片低到中等感知区分，卡片与容器低但可辨，按钮与表面明显区分。玻璃感优先使用稳定结构基底叠加已有低透明环境光和弱描边；原本不透明的表面保持不透明。

`mid-light` 和 `mid-dark` 必须保留画面重量。禁止从中央主体高光生成苍白页面，也禁止从底部/边缘局部暗色生成近黑页面。

容器的颜色必须落在真实 `visualSurfaceCarrier` 上。若底色由异形 Rectangle/Vector/Boolean 承担，只修改该层；不得给无圆角外层新增 Fill，导致方形底或轮廓扩大。

## 5. 卡片氛围唯一规则

`cardAtmospherePalette` 与 `interactionPalette` 分开。卡片氛围只来自新 KV 大面积环境色及其邻近色；禁止从标题、人物、箭头、Logo、金属包边、按钮色和局部镜面反光取色。

普通卡顶部/标题区、收益复合卡底部是可复用载体支持时的默认氛围锚点，不是搬动原有图层的指令。已有不同空间家族时按既有几何与 KV 光照组织配色并记录理由；同模式保持原空间配方。标题文字和氛围层是两个角色：普通卡片标题默认使用 `textBaseColor`，通过原字号、字重和位置建立层级；只有原稿已有独立标题强调或存在明确业务/主题证据时才登记 `titleAccent`。标题即使使用强调色，也只能是稳定纯色或视觉近似纯色的窄差渐变，只允许边角小范围高光；不得横跨标题使用大幅多色扫光，也不得因为按钮、数字或 KV 金属为金色就自动把标题改成金色。

卡片顶部包边、角饰、标题装饰线、顶部光带及其他卡片 Chrome 与标题文字仍是不同角色，但都默认归入表面/氛围家族：这些装饰从背景、卡片和 `cardAtmospherePalette` 的邻近环境色派生，不继承 `dataAccent`、Icon 或 `buttonPrimary`。只有原稿已有明确业务强调且新主题仍有对应证据时才登记小范围例外；不得因页面选择金色按钮或数字，把重复卡片顶部统一刷成黄色/金色边圈。

四种转换：

| `themeTransition` | 氛围处理 |
|---|---|
| `light-to-dark` | 稳定表面使用有环境色相的深底；将已有浅色雾化层重着色为可感知的局部有色受光，而非把基底、按钮和所有反射一并压暗。受光区域按既有载体与光照证据组织，默认锚点见上文；白色全幅罩染不得形成灰雾，塑形暗部不能吞掉受光区。 |
| `dark-to-light` | 稳定表面先成为干净浅底，再逐层判断旧光影/形状是 `keep / fade / remove-visually`。只有仍能解释新 KV 环境光且不会制造顶部暗块的层才保留；保留层重着色为非常淡的环境邻近色，冗余纯装饰层允许把既有 Paint opacity 或全部色标 Alpha 降到 `0` 以视觉移除。优先减少层数的可见贡献，不要求把深色 UI 的每道光影都迁移到浅色 UI。清除旧深色端点、`#000000`/近黑无彩端点、暗色 Effect 与暗纹理位图造成的脏罩染；向稳定底色/原透明边缘消隐。结构蒙版/Boolean 几何可保留黑色，但任何实际输出像素的卡顶氛围都必须在 1:1 与整页截图中证明为轻微环境光，不能把顶部染成暗了一块、灰带、厚重光斑或高频形状。 |
| `light-to-light` | 保留渐变类型、方向、范围、色标数量/位置和有效开关，重着色为环境色；存在合成罩染问题时仅按下述已登记材质强度例外调整 Paint Alpha。 |
| `dark-to-dark` | 保留原光影空间配方和有效开关，重着色为新 KV 光色；存在合成暗沉/灰雾时仅按下述已登记材质强度例外调整 Paint Alpha，不重做结构。 |

跨模式允许修改已确认 `card.atmosphere` 的既有 SOLID/GRADIENT Fill 色彩及 Paint 强度；GRADIENT 可按转换目标调整配方。登记 `mutationPlan.atmosphereMutations` 的层职责、原/目标 Paint opacity 和色标 Alpha、背景及合成问题。SOLID 模糊光斑也是氛围载体，不能因不是渐变而漏掉。两种同模式只允许重着色，以及为已证实合成问题登记的 Paint opacity/色标 Alpha 强度修正；渐变类型、transform、色标数量/位置不变。

上述例外均不改承载节点几何、层级、混合模式、节点/祖先整体透明度、蒙版类型/Alpha/几何、稳定前后表面的不透明性，也不新增/删除 Paint 或激活隐藏层。只有 `dark-to-light` 中被明确判为 `remove-visually` 的纯装饰 `card.atmosphere` Paint 可以把既有 Paint/色标 Alpha 归零；稳定卡片底色、结构表面、功能边界、蒙版和非氛围材质不得借此归零。不能把保护结构透明度误解成氛围强度，也不能将蒙版灰色当作可调灰雾。氛围位图另按《Figma 执行规范》的 IMAGE 分类处理；暗纹理若不适合浅色主题，须按分类降低既有可见贡献或视觉移除，不能只给父级换亮色。

表面深浅和按钮仍是独立配方，但服从目标模式：深色 UI 可配明亮彩色、干净浅色或有依据的干净深色按钮；浅色 UI 的主要按钮/CTA 先比较鲜亮高彩主体，当 KV 与页面整体偏浅时，默认改用有主体/标题/金属证据的干净深色主体，只有真实宿主证明鲜亮方向仍能清楚突出时才保留。实际明暗、主体彩度、受光及字色在新宿主背景重新试色，不能沿用旧模式按钮暗部面积；深色方向若灰闷、近黑、缺少稳定中间调或只剩亮边即失败。完整叠层审计和覆盖方法见[《叠层合成审计》](composite-layer-audit.md)。若固定几何/节点 Alpha 仍使可感知光色或清楚按钮无法成立，记录具体结构冲突与试色证据，不降低验收标准或越界改结构。

浅色→深色且收益卡没有可复用氛围 Paint 时，可在收益卡最外层稳定表面末尾增加最多一个低透明底部渐变 Fill；不得加在前景异形叠层或其他卡片上。

与新表面家族冲突的旧主题氛围即使 Alpha 很低也必须换入 `cardAtmospherePalette`；低透明不是保留理由。旧主题残留扫描必须同时覆盖 Hue 与无彩明度：黑色、近黑灰、低明度中性色、暗色 Effect 和主题装饰 IMAGE 的最终可见贡献均要分类，不能因它们没有旧主题 Hue 或名称像蒙版就跳过。

## 6. 文字系统

普通文字默认共享一个 `textBaseColor`，用有效文字强度建立阶梯。下表是起点，不是所有背景/原节点必须照抄的 Paint Alpha：

| 角色 | 默认 Alpha |
|---|---:|
| `text.primary` | 100% |
| `text.secondary` | 80% |
| `text.tertiary` | 60% |
| `text.muted` | 40% |

- **文字基色按目标 UI 模式硬分流。** `targetUiMode=light` 时，普通文字选择带 KV 冷暖倾向的深中性 `textBaseColor`，优先保持已经确定的 Hue/冷暖与合理 S，通过降低 HSB 的 B 建立深度；稳定基色默认控制在 `B 18–32`。`text.primary` 使用该基色的 `100%` 有效文字强度；白色、近白及其他浅色卡片上的 11–14px 主文案若在 1:1 仍显淡，先继续降低 B，不先降低 S、降低 Alpha，也不改用与表面协调但处于中间明度的灰绿、灰粉或灰蓝。
- `targetUiMode=dark` 时，普通文字的稳定 `textBaseColor` 色标保持 `B=100`，Hue/S 只用于承接 KV 的冷暖或轻微色相倾向；`text.primary` 使用 `100%` 有效强度，`secondary/tertiary/muted` 再从同一 B=100 基色通过有效 Alpha 建立层级。不能为了柔和、统一或减少抢眼而先把普通文字基色降到 B<100；若文字在真实深色宿主上过强，先核对角色是否应归入次级档及其有效 Alpha。
- 上述 B 门禁约束普通正文基色，不约束精确保护文字、按钮字、链接、语义状态、`titleAccent`、`dataAccent` 或复杂图片覆盖文字；这些角色仍须登记自己的配方与宿主证据。浅色 UI 因特殊有色/复杂背景无法共用 `B 18–32`，或深色 UI 因非深色局部宿主不能使用 `B=100` 时，必须登记局部 `textBaseColorOverride`，不能静默改变全页基色。
- 通常只调整文字 Paint Alpha；先计入原节点与祖先 Alpha，不能重复弱化。仅普通 TEXT 自身强度可按[《文字换色与恢复》](text-color-recovery.md)最小例外调整，状态/祖先/保护 Alpha 不变。
- 复杂背景先选择合适的文字方向与有效强度，必要时联合调整已允许的背景；记录 `textRampOverride`。确实无法共用 RGB 的非等价背景可登记局部 `textBaseColorOverride`，说明背景、角色和可读性依据；不逐组件任意配色，也不把全部文字拉成同级不透明。
- 价格、规则、必读和可操作信息不得因套用弱化档而难读，不以某个固定 Alpha 判断其业务可读性。
- 同级任务文字、认证/状态文字和 KV 衔接文字使用相同普通文字角色，不因组件来源产生任意颜色。
- 按钮、链接和真实语义状态文字独立处理；`protected-media-overlay` 与 `protected-rank-top3` 中的文字保持原稿 Paint，不套用新文字阶梯。
- 普通卡片标题默认使用 `textBaseColor`，以原字号、字重和位置区分正文；只有原稿已有独立强调或存在明确业务/主题证据时才使用 `titleAccent`。关键收益/核心数字使用 `dataAccent`。`titleAccent` 与 `dataAccent` 均不得机械互用，按钮/Icon/金属色也不会自动授权标题跟色。

### 6.1 强调数字：跨 KV 的独立规则

所有主题下，金额、奖励额度，以及任务/作品模块中原稿通过加粗或突出颜色表达的数字，均识别为 `data.emphasis`；不限于大字号或鲜活 KV。以原稿业务语义和文字区间确定角色，不把所有数字、日期、编号或整段正文都升级为强调数字。保持原字号/字重，仅独立调整对应 Paint。

这些数字应使用鲜明、有色彩力度且清晰可辨的强调色；不能为了普通正文的对比度参考数值不断压暗，造成灰闷。按《验收规则》第 5 节以实际可读性与强调效果验收，对比度按第 5.1 节适用策略逐项验收，并作为辅助选色证据，不以最高数值选色。强调色随新 KV 选择，不固定具体 Hue；亮色也不是简单加白、降低彩度或提高透明度。`targetUiMode=dark` 时，高亮数字的公开 `number` 锚点必须与从背景环境提取的 `icon` 锚点同 Hex/RGB；提案前应在数字与 Icon 的真实宿主上共同验证清晰度，若冲突先调整允许的宿主/共同锚点，不能选定后让数字或 Icon 单独漂色。

顶部收益卡仍需看实际背景和整体层级：浅色 UI 中字色可亮可深，不预设深色更高级；选深色时应干净、明确，不能落入浑浊中间调。深色 UI 的高亮数字继续使用已选 `number=icon` 代表色，不能因该卡宿主不同临时造第三强调色；若代表色在此不清楚，方案必须在 Phase 2/3 解决共同锚点与合法宿主关系，而非落稿时单独压暗数字。该卡与其他强调数字同样按实际清晰度与强调效果验收，不设默认数值门槛。

### 6.2 亮色鲜明、深色干净，避免灰闷的中间调

强调色必须保有充足的饱和感，并联合控制感知明度；不能把“高饱和”与“明亮”混为一谈。低彩度更容易显灰，低明度更容易显暗，两者共同影响灰闷观感。不得仅因协调、克制或对比度数值而降低强调色的彩度或持续压暗。

在 HSV 取色面板中，向右通常提高饱和度 S，向上提高明亮度 V；上方偏右可寻找鲜亮方向，右下方可寻找带色相倾向的深色。面板位置只是选色辅助，不是固定坐标配方。HSV 的 V 不等于感知明度，也不等于计算文字对比度的相对亮度；量化时可用 OKLCH 的 L 与 C 分别比较感知明度和彩度，不能混用不同空间的数值或设统一跨色相的最低饱和度。

- 亮色方向：保留清楚的色相和彩度，明亮、有精神；不要只加白、降 Alpha 得到粉灰。
- 深色方向：形成明确深度与清楚轮廓，保留恰当色相倾向；不是把鲜亮色略微压暗后就当作深色方案。
- 中间调可用于过渡、阴影或有依据的辅助角色，不自动禁止；但不能成为强调色的默认折中方案。
- 不能仅凭 HSV 饱和度判断“灰”。较高饱和度但感知明度偏低的颜色仍可能在浅表面上显得沉闷；须结合明度、背景、面积与同页亮/深两端观察实际效果。
- 方向存在关键疑点时，对照鲜亮方向与干净深色方向，在相同背景和尺寸下确认角色；已有充分证据时不强制额外试色。不以取色器位置直接判通过，也不机械把所有颜色推到色板边缘。

## 7. Icon 材质

功能 Icon 必须进入新主题；图片 Icon、Logo、头像、封面和插画保持不变。

- Phase 3 为每类功能 Icon 冻结 `iconPairPlan`：卡片宿主、底托稳定面、图形稳定主体/高光、目标相对重量和代表实例。先在同一真实视觉单元中联合选择底托与图形，再分别写入；不得先锁定荧光 Icon，随后靠压深底托补轮廓，也不得先做偏重底托再用更亮 Icon 抵消。
- Icon 容器与 Icon 图形是独立角色。容器是低强调辅助表面，视觉权重低于 Icon 图形、小按钮、选中态和 CTA。
- Icon 容器不得直接复用高饱和按钮色后只降低节点 Alpha。按与卡片合成后的实际明度、色度、面积和重复频率决定。
- Icon 图形不能直接复用小按钮渐变。它应引用或有依据地派生自 `schemeAnchorContract.icon`；`icon` 锚点在 Phase 2 从连续背景环境家族派生，按真实宿主上的轮廓分离、状态、重复面积和整页协调决定明度、彩度与材质。深色 UI 的高亮数字代表色直接复用这一 Icon 锚点，而不是重新取一条独立亮色。`icon` 表示可编辑的功能 Icon 图形，不表示底托，也不授权图片 Icon、Logo、头像或插画染色。图形须与容器、文字及按钮清楚区分。
- 多层 Paint 分别承担 `base / shadow / material-band / environment-reflection / specular / edge-highlight / border`。根据原渐变类型、方向、明暗和彩度判断职责，不按数组索引机械映射。
- **所有可见 Icon 渐变逐色标保差。** 不限金属材质：原稿任意可见 Gradient 若至少两个有效色标 RGB 或 S/B 不同，Phase 3 必须为每个 stop 单独登记目标；目标可换 Hue，但不能让原本低 S/高 B 与高 S/高 B 两端变成同一 RGB、同一 S/B 职责。Paint 类型、stop 数量、位置与 gradientTransform 保持只证明结构未变，不证明渐变仍可见。
- **先保金属色标关系，再套六色锚点。** 原稿有可见金属/镜面梯度时，记录每条有效渐变的色标角色和原有相对明暗；`schemeAnchorContract.icon` 仅约束稳定主体色标。暗端、材质带、反射和高光须各自从新 KV 光色派生，不得按原色标亮度阈值把一整条渐变的多个端点量化成同一目标 RGB。写入前检查目标色标仍有可解释的受光差异；代表试色和最终实例执行 `scripts/material_stop_audit.py`，再以原生 1:1 原稿/副本对照确认金属体积与镜面带仍可见。该脚本只抓明显色标塌缩，不代替视觉材质验收。
- 保留原稿材质的明暗分工及可感知层次、高光覆盖范围、位置和方向；按第 3.2 节判断是否需要浅→浅比较基线，其余情况结合 KV 与宿主联合调整 H/S/V；保留透明度与空间结构约束。禁止把旧色明度机械插值到某个预设的高明度低彩端后直接当成新材质，也不能用截断插值让不同色标落成同一颜色。主体本色、塑形暗部和高光分别识别：浅色原主体不自动变成新主题的无彩高光。仅保留层数但把各层压成相近暗色、相同渐变或低 Alpha，视为材质丢失。
- 对明亮材质，检查主体受光面是否有鲜明颜色，阴影是否只在必要塑形区域，高光是否在实际尺寸下可见。不能把所有可编辑面统一深色后，仅靠一条浅边宣称保留立体感。底托的轻与图形的鲜明分别设计；参考图片 Icon 的光影不等于目标可编辑 Icon 已实现相同质感。
- Icon 不得发闷、过深或成为压过主要操作的重复焦点。
- `targetUiMode=light` 时，Icon 的可见主体、中间调、材质带和大面积塑形暗部不得使用黑色、近黑灰或低明度脏色；结构蒙版的黑色不计入颜色角色，但任何真实参与输出的低明度层都须重着色。允许保留少量用于轮廓/体积的局部暗部，但其面积、位置和最终合成不得让 Icon 看成暗块、脏金或只剩亮边，且必须在 1:1 与重复排列中复核。

### 7.1 Icon 底托独立配色

本节适用于图形背后的小面积容器、底托和既有承托渐变，不包括整张卡片、大面积内容容器、卡片氛围层或受保护的前三名形状。先确认真正的承载节点，再单独制定 `iconMaterialRecipe.container`；它不自动继承页面、按钮或 Icon 图形的 Hue。

普通辅助底托拥有独立 Paint Recipe，但颜色选择必须与实际 Icon 图形联动，不得各自通过后拼接。原稿无彩底托不意味着新主题必须继续无彩度；可以使用有 KV 来源的有色表面，仍保留原 Alpha、材质空间结构与几何。中性色保留要求限于结构职责、精确保护或当前任务明确锁定的通道，不扩展为图形/按钮或所有辅助底托的默认固定配色。不能仅因目标模式改变，就把所有底托统一映射为同一中性色或固定 V。

- **候选来源。** 可从 KV 的环境色、稳定辅助色、主体/材质中间色、环境反射及协调的冷暖中性色中推导底托色，不必逐像素照抄。颜色须有可解释的 KV 或已授权参考关系；局部强光只能按其局部职责使用，不能把偶然亮点或品牌专属色直接铺成底托。
- **按承托效果选择。** 结合实际 Icon（包括保持原样的图片 Icon）比较同色系与有依据的异色系/中性方向；从有证据的方向中选取，不强制每次凑齐所有色系。重点看图形轮廓是否清楚、色彩能否相互衬托、底托与卡片是否融合得当、整页冷暖和彩度是否平衡。不能仅凭“主色加白”或“同色最协调”直接定案；同色方案成立时也不为追求变化硬换异色。
- **低强调不等于固定浅色、深色或低饱和。** 用实际面积、重复频率、明度/彩度和边缘关系控制视觉权重，使底托服务图形，并成为 `Icon 底托 < 选中 Tab < 主要按钮/CTA` 中最轻的一层。深浅、冷暖及彩度由当前环境决定，不固定采用某一种淡色或灰色；不能所有底托都变成灰白，也不能让底托抢过图形或接近 Tab 的状态强度。分别验证底托↔卡片的环境关系、底托↔Tab 的相对显著性与图形↔底托的轮廓/承托关系，图形能看清不等于底托与页面协调。
- **浅色 UI 的底托要淡而可见，不能暗沉或消失。** `targetUiMode=light` 时，普通功能 Icon 底托从页面/卡片环境家族或有依据的协调方向取一层轻颜色；不要求使用抽象的“高调”口径，也不设固定明度差。低强调不等于近零对比：在 1:1 下暂时忽略 Icon 图形时，底托的轮廓或表面仍须与卡片清楚分离；不能同时使用过浅颜色和极低有效 Alpha，把合成结果淡到看不见。弱化优先使用适度较低彩度、较小面积、柔和边界和原有材质，但须计算最终合成色而非只看 Paint 值。必须在实际尺寸、灰度、模糊和整页重复中确认它既没有形成灰粉、灰蓝、近黑的沉重色块或高频暗点，也没有融进卡片、让重复实例像缺少底托；出现任一问题时按真实宿主调整，不用单一数值覆盖观感。
- **渐变承担可见职责。** 在既有渐变结构中，用有色承托区、受光区及向周围表面的过渡建立层次；终点可以是协调邻近色、中性色或原有透明过渡，不要求总是“主色浅色 → 白色”。如原稿没有渐变，不为模仿参考新增渐变；已有渐变的几何、色标位置、有效开关、Alpha 与节点结构继续服从既有换肤边界。
- **同族一致与例外。** 同类底托通常共享一套配方。仅在图形素材、语义或背景确有差异时使用有依据的变体，避免逐个任意换色形成杂乱色盘。前三名底托仍按原 UI 保护，不能套用本节重着色。

在 `iconMaterialRecipe.container` 与 `iconPairPlan` 中记录颜色来源、图形/底托/卡片的合成关系、各自 H/S/B 方向、基底及渐变色标职责、选择理由与代表节点；Phase 5/7 必须用同一截图同时验证 `gradient-stop-collapse / container-too-heavy / pair-low-separation / pair-over-salient` 四类失败以及整页重复排列。若同色系造成糊成一片或缺少层次，须实际比较有依据的其他方向；若异色造成割裂，则回到候选修正。不同于环境主色本身不构成不协调或旧色残留，须对照已选角色色板和真实渲染判断。

## 8. 按钮与 CTA

先由整套候选决定交互色相家族 `hueStrategy`，再用原稿已有 Paint 实现 `materialStrategy`。材质与色相分开：玻璃、卡通、金属不自动推出蓝、红或金。

按第 3.2 节结合目标 UI、KV 明暗/色彩力度与实际宿主选择 H/S/V。先冻结主要操作共同的 `buttonPrimary` 代表色、主体色相和中间调，再按小按钮和 CTA 各自原有层结构建立材质配方；适用的浅→浅场景先比较仅换 H 的基线，只有真实通过时才沿用，否则调整必要的彩度与明度。原透明度、渐变结构和材质分工默认保留，下文的 Alpha 修正仅在任务允许的对应范围执行；调整 H/S/V 不授权越界改透明度或结构。

**任务级用户配色偏好。** 只有用户在当前任务明确指定某个角色的色相、品牌色或候选顺序时，才将其登记为该角色的优先候选；题材名称、文案语义或材质名称本身不自动产生色相偏好。该偏好仍须结合 KV 稳定色、整体冷暖与明暗、操作显著性、真实背景和材质合成验证，不扩散到未指定的卡片、Icon、底托或保护区。若偏好与可读性、层级或结构约束冲突，保留试色证据并说明冲突，不静默改成另一色相。

- 卡通方向可候选更明快纯净的辅助色，按角色、面积和 KV 气质分配彩度；不机械套最高饱和度，也不把鲜亮本身判为幼稚或刺眼。
- 玻璃/水晶方向可从稳定材质中间色或辅助色建立基底，把虹彩、粉光、青色亮边等限制在已有局部高光层。
- 主体具有强材质视觉时，可把该材质的颜色关系作为 Icon/按钮候选，但不能从材质名称推出固定 Hue 或 HSV 区间。用户只要求某种材质感而未指定色相时，结合 KV、环境与真实宿主比较有来源依据的方向。材质感来自明暗分段、局部高光、环境反射、边缘关系、方向渐变和适度冷暖变化，不来自某一个 Hue。

当主体或标题呈现明确、显著的金属视觉时，建立 `metalAccentEvidence`：记录来源节点/区域、金属家族判断、稳定本色、中间调、塑形暗部、镜面高光、面积/重复/主题级证据与可信度。仅有材质名称、文字语义、一个小亮点或局部金属包边不成立。证据成立后固定生成三案：`metallic-analogous` 从真实金属关系生成同色系金属按钮；`gold-bright` 生成正常明亮金色按钮，优先以类似 `#FFEED7→#FFC58A`、`#FFEEC6→#F9DB92`、`#FFE5A3→#FFC165` 的暖亮范围建立候选，再根据 KV 光照、按钮原材质和真实宿主微调，示例不作为固定模板。主体中间调必须明确为金黄并保持较高感知明度和彩度，暗铜/棕橙/土黄不得通过；`clean-deep` 从 KV 中有来源的深色家族生成清楚、稳定、带彩度的深色按钮。三案各自在真实宿主上验证，不能以“浅页面需要压住”为由预先删除明亮金色，也不能把金色整体压暗后仍标成 `gold-bright`。银蓝灰与蓝色页面若同属一个综合色相家族，只能标为同色系金属；深浅变化不构成撞色。

某个材质色进入候选不代表它优先胜出；原稿材质的旧色相也不构成新稿沿用的依据。Hue 有疑点时在同一 Icon/按钮宿主比较有来源依据的方向，按第 3.2 节以基线或调整后的 H/S/V 验证，仍保留 Alpha、结构及明确锁定项，不为套材质名称牺牲实际显著性。不要把一次任务的成功或失败色相变成后续默认方案。

同族主要小按钮与底部 CTA 的主体必须共同引用 `schemeAnchorContract.button`，共享同一个代表色、主体色相和稳定中间调；不是只要同属暖色或金属就合格。不同处主要由原有尺寸、渐变、受光与局部反射表达。CTA 可具有更丰富的现有材质层，但不能因此单独换成明显更浅、更深、黄色对橙色或另一套主体色系；次级/禁用按钮按原稿明确的角色另行分类。Paint Recipe 按各自原有层结构实现，但主体不得漂离共同锚点：

明确的禁用按钮不建立新的灰色、米色、低彩或低 B 色板。先让禁用态完整继承对应正常按钮的 Fill、Stroke、Effect、文字色和材质色标，再对最小完整按钮视觉单元应用相对正常态 `50%` 的整体有效透明度，保证背景、文字、高光与边界同步衰减。优先使用该状态根节点的 opacity；若组件结构已通过等效祖先/状态 Alpha 达到 50%，只记录并复用，不再乘一次 0.5。不得把半透明后的合成色读回当成新的禁用色锚点，也不得用改变各 Paint RGB 近似模拟 50%。该例外登记为 `disabledButtonOpacityOverrides`，包含正常态映射、禁用态根、原/目标有效倍率与防重复计算证据。

CTA 的判定按操作语义和可编辑视觉单元进行，不因它位于营销 Banner 实例或促销构图内部而失去按钮身份。营销 Banner 的创意背景/插画/营销文案可保护，独立可编辑的 CTA 仍进入按钮全量覆盖、代表试色和残留检查；只有 CTA 已烘焙进不可编辑单图，或用户明确要求整个 Banner 连同操作控件保持原样时，才从换肤集合排除。

先登记共同的 `interactionFamilyId`、`buttonPrimary`、来源锚点和主体色相方向，小按钮/CTA 只为暗部、高光、反射和材质复杂度派生局部色标；不能为两者各自选择不同的按钮代表色后，只用宽泛的冷暖标签声称同族。主体关系进入机器目标值与外观校验，最终合成主体区域仍须并排比较。原稿或用户明确的非等价宿主变体事先说明，不能在失败后用材质名称拆出新家族。

- 小按钮使用容易辨认的主体色与适量高光；有 KV 依据的邻近色渐变可以贯穿按钮。稳定基底不等于纯色、深色或几乎不可见的色差；限制的是无光照依据、破坏主体统一性的杂乱多色扫光，以及吞没轮廓的亮框和不必要阴影。
- CTA 在原有层中强化基底、局部色光、窄高光、边缘亮线和光泽；不能把小按钮等比放大，也不得新增原稿没有的效果。区分有彩度的受光基底、不同区域的环境反射和局部高光；有依据的环境色光可丰富材质，不必把所有层压进同一深色。具体颜色及冷暖关系由本次 KV 决定。
- 当前可用的全局 CTA 必须成为最强操作焦点，主体显著性强于普通 Tab、类别栏、容器和装饰；小按钮在各自卡片内也应强于弱控件。须在 1:1 与整页缩略图核对颜色和材质形成的差异，不能只靠大尺寸或可读的字宣称突出，也不能成为与 KV 无关的最大饱和色块。

按钮背景和文字必须作为组合生成、试色和淘汰。每套至少考虑一个协调浅色文字和一个协调深色文字方向：浅色可为纯白、暖白、冷白或带主题倾向的近白；深色可为深中性或深主题色。无金属撞色中被 KV 来源、彩度/明度、面积和真实宿主共同证实为**特别鲜艳**的按钮，设置 `buttonTextPriority=vivid-contrast-white`，小按钮与 CTA 优先共用纯白/近白方向；白字在真实文字覆盖区对比度不足时再试深字，凭可读性和按钮材质效果的对照证据定案，不能只因深字静态数值较高便跳过白字。其他按钮设置 `buttonTextPriority=contextual`，依据按钮材质、宿主和字号选择浅字或深字，核对同族小/大按钮关系，不强制先试白字。`buttonVariant=gold-bright` 另默认深棕字，并在渐变最亮、最暗和实际文字区验证；只有深棕真实失败且有明确证据才允许其他方向，不得为保白字把亮金压暗。禁用、次级、描边或明确浅底按钮单独分类。

分别检查渐变最亮端、最暗端和半透明合成背景，并标明它们是否落在实际文字覆盖区域。按《验收规则》第 5 节验证真实可读性；须核验第 5.1 节适用策略的对应对比度要求；用户另有标准或具体比值时同时执行。文字验收取文字实际覆盖范围内的最差有效背景，不把远离文字的装饰亮边当作文字背景，也不能漏掉真正穿过字形的亮带。最终选择同时服从 KV、按钮材质、周围表面、显著性、可读性和审美；不能只因背景“看起来深/浅”机械选字色，也不能让单一最高数值自动胜出。

真实可读性与适用策略的对应对比度要求分别验收；WCAG 固定比值不是默认门槛，对比度也不是越高越好的审美评分。提高白字清晰度时，必须同步复核主体明度和受光感，不能只靠不断压暗整个按钮、削掉所有反射来过关。应联合比较更明快基底与深色字、既有渐变中适合文字区域的配色及其局部反射。不得改字号、字重、几何或文字位置兜底；仅用户明确要求的数值门槛不得擅自下调。若结构内无法兼顾实际目标，记录具体冲突和已试方案，不把数值较高包装成视觉通过。

### 8.1 必须检查实际合成后的色彩力度

在 Phase 2 提案预检、Phase 3 配方规划、Phase 5 试色和 Phase 7 验收时，区分基底的色相、彩度、明度与材质反光，逐项检查：

1. **基底必须具有足够的有效彩度与明暗力度。** 结合 KV 的视觉气质与按钮角色判断，达到第 3.1 节的操作焦点要求；不能只取局部浅色反光，把主体稳定中间调全部去掉。色板中的数值仅作证据，最终看渲染结果。
2. **高光是否把颜色冲淡。** 读取实际叠层的 Paint/色标 Alpha、节点/祖先 Alpha 和 blendMode，查看 1:1 合成截图。尤其检查原有白色、暖白或淡色反射叠到新基底后，是否使大部分表面泛白、发奶或丢失色彩层次。保留层数不等于保留材质力度，亮度高也不等于颜色鲜明。
   同时检查相反失败：是否为避免泛白而压暗基底、把所有反射统一减弱，造成明亮 KV 下的按钮沉重、像未受光的暗块。高光 Paint 的 Alpha 大不等于覆盖面积大；判断其空间分布、颜色、混合与最终贡献，不能机械限制成统一低 Alpha。有彩度的反射与白色罩染效果不同，须分别试色。
3. **按钮必须与新背景明确分离。** 背景色改变后重新建立足够的明度、彩度、色相及边缘对比，不能假定原按钮在旧背景上的显著性仍然成立；同属暖色或同色相并非失败，关键是最终区分程度。
4. **主要操作是否足够突出。** 与邻近 Tab、标签、图标容器及已有禁用态比较；启用按钮不能看起来像弱标签或待解锁按钮。CTA 的突出是业务目标，不能仅因比卡片醒目就判为“喧宾夺主”。

发现过度柔化、暗沉或层级不足时，先定位贡献来源，再在同一代表白名单上针对基底、反射/高光或背景关系修正并截图。基底问题调整其明度/彩度，罩染问题调整对应层颜色和允许的 Alpha，色相关系不合适时比较其他有依据的色相；不机械规定每次先改基底或先降高光。联合调整须记录变量及作用，不能只换字色、继续叠加泛白高光或只写分析理由就宣告问题解决。保留修正前后图及最终选用配方，不能把未经试色的推测当成淘汰证据。

按钮材质强度修正登记 `buttonMaterialAlphaOverrides`，仅限已识别的高光、反射、局部罩染或塑形暗部：既有 SOLID/GRADIENT Fill/Stroke 的 Paint opacity、渐变色标 Alpha，以及已有带颜色 Effect 的颜色 Alpha。记录确切节点、通道/索引、层职责、原/目标值与合成证据；不能只给整个按钮一个统一强度系数。不改节点/祖先整体 Alpha，不降低原本不透明的基底或结构表面，不增加/删除 Paint/Effect，不改渐变类型/几何/色标位置、Effect 几何、蒙版或原零/非零开关；禁止激活原透明部分或把原可见层归零。此强度例外适用于四种深浅关系，但不授权结构重做。卡片氛围、保护区及其他结构仍遵守各自规则。

把检查结果记录为 `themeDecision.buttonCompositeReview`，包括代表节点、实际背景、基底/高光职责、合成前后证据、与邻近控件/禁用态的比较、足够彩度与对比度如何成立、主体明度及受光感、`buttonToneDirection`、针对实际问题的对照试色及变量、修正或接受理由。浅色 UI 的主要按钮/CTA 可使用明亮高彩方向，或在偏浅宿主上使用有 KV/金属证据的干净深色方向；后者必须比明亮候选形成更清楚的操作分离，并保持色相、彩度和受光。功能 Icon 图形按角色清楚，底托遵守淡淡带色且不暗沉。因失去层级而发灰、泛白、灰黑，或与 KV 光照气质不符而暗沉的方案必须失败，文字对比度合格不能覆盖这一失败。

## 9. 标签、Tab 与颜色保护区

- **先确认等价关系，再按新 KV 换色。** Phase 1 的同一 Style/Variable 和同 RGB 检索只提供候选关系，不能仅凭它们把不同角色强制合并。`sourceAudit.sourceColorRelations` 只登记确需保持的连续同色表面，及同角色、同状态、同材质和等价宿主中对应的同色通道；原稿颜色不是新稿取色依据，也不是锁定旧色相的指令。
- **同族控件跨区域统一。** 内容卡分类 Tab 与榜单卡 Tab 等，按控件家族、层级、状态和材质建立共同新配方，不以所在卡片名称/位置分别调色。同族同层级同状态原本同色的对应通道，继续放在跨区域同色组中；颜色仍根据新 KV 调整。不同层级/状态可以保留轻重差，但色相家族与选中语言应一致，不能一个灰深绿、另一个亮薄荷绿。不同角色的按钮、Icon 或一级异形底板不因都可点击而强制同色。
- **Tab 默认归属表面家族。** `schemeAnchorContract.tab` 从页面/卡片表面家族或邻近色派生，选中态通过明度、彩度、边界、文字或既有指示条形成信号；撞色按钮不自动授权 Tab 使用同一撞色。只有用户明确要求或强业务语义证据时，才可在方案选择前登记例外及其面积限制。
- **浅色 UI 的 Tab 淡淡带色、不得暗沉。** 选中底板仍归属页面/卡片表面家族，通过轻微明度/彩度差、边界、文字或既有指示条表达状态；它必须比普通 Icon 底托更明显，又弱于主要按钮/CTA。不要求抽象的“高调”，也不设固定明度差。实际尺寸、灰度、模糊和整页重复中不能形成灰闷暗条、沉重色块或高频暗点，也不能与底托或按钮看成同一强调等级。
- 宿主稍有差异先联合调整合法背景并试共同控件配方，不能只因局部对比度需求就独立改一处选中底色。确实无法共用时，写入前登记变体的背景/状态职责、共同配方的失败证据与范围；变体延续同族色相及状态语言，真实跨区域差异不过大。卡片独立、尺寸/节点类型不同或局部修正方便不构成拆组依据。共同新配方可用于原稿不同 RGB 的同族控件，此时以声明的目标配方校验，不伪造源 RGB 等价关系。
- **统一新配方，不冻结旧颜色。** Icon、按钮、卡片等各自依据新 KV 和真实宿主选择新颜色；确定配方后，等价实例的对应通道一致。同一连续 Tab 底板拆为多个节点时不能漏改/拆色，同族材质的不同明暗色标仍保留原层次，不能压成一个 RGB。跨角色偶然同色、共享旧 Style/Variable 不要求新稿仍同色；同族遇到非等价背景、材质或业务状态时可以建立有依据的变体，在写入前登记对应范围及理由，不是用户审批点。节点类型、宽度或名称本身不构成变体依据。
- 原稿同 RGB、用 Alpha 区分状态的同一文字系统，默认使用共同新 RGB 并保留状态 Alpha；若新 KV/状态可辨性需要独立状态色，在 Phase 3 按状态职责登记方案并在真实宿主试色，不改变状态/祖先 Alpha，也不自动将所有选中态升级为强调色。
- **可辨与对比度不回退分别验收。** Tab/连续容器与外卡、选中与未选中底色、指示条与所在底色、文字与实际背景分别比较，按《验收规则》第 5.1 节分别执行适用策略；内部同色或文字可读不能抵消边界/状态失败。原稿自身差异较弱时，即使同模式达到其数值仍需通过真实可辨性，不沿用原稿的看不清问题。保持连续表面同色，用 KV 家族内适度明度/彩度差拉开外卡，避免一起洗成近白。执行定义见《验收规则》第 5.1 节。
- **Tab 是完整控件，不只是文字。** 识别前景异形底板、后景未选表面、相连内容底板、文字和指示条的真实承载层。同一连续表面原来同色，换肤后仍同色；原来有区别的前后表面保留可感知区分。指示条进入状态角色，不能落入通用装饰色。一个同族代表通过后核对其余实例的全部对应通道，不能只对照 Tab 文案。
- **保留关系的方向与作用。** 原稿选中信号强于未选中时，新稿仍须更突出；不能因选中/未选中各自对背景的比值都提高，就放行强弱倒置。选中不等于必须更深：结合原稿底板、文字、指示条的共同信号判断。可比较的同宿主强弱顺序按《验收规则》第 5.1 节冻结并机器比较；其他材质/业务层级按完整彩色与灰度对照验证。跨模式可反转明暗，不反转操作优先级。
- 配方先解决整组的连续、状态、嵌套和材质关系，再派生各层目标色；包括深层列表底色。局部修正按执行工具第 4.8 节继承全部关联约束，不能只重验修改的两个外层，或临时从同色组删除失败成员。
- 同色关系使用[执行工具第 4.6 节](execution-workflow.md#46-同色关系检查)在计划预检及实际读回后核对；1:1 原稿/新稿局部对照同时检查接缝、状态和层级。数值一致只证明登记通道同色，不证明映射完整或合成后观感正确。
- `control-family-consistency` 检查同时并排看内容卡、榜单卡及其他同族实例的原稿/新稿 1:1 彩色片段，核对选中底色、文字、指示条和未选状态的共同语言，再检查整页。各局部可读不能代替这项通过；共同配方修改后，相关其他卡片中的实例一起失效复验。
- **方案锚点必须逐通道兑现。** `schemeAnchorContract.tab` 不是“与它相近即可”的建议值。每个公开锚点都须至少绑定一个稳定可见的 `anchorId` 通道，其目标 RGB 与用户所选方案完全一致；Tab 的主要选中底板不得在执行阶段改绑到 `button` 或 `icon`，也不得因按钮更醒目就直接复用按钮色。渐变暗部、高光和反射可围绕锚点派生，但不能把稳定主体的代表色改掉。代表试色后与最终审计都读回六个锚点，缺失、错绑或目标值漂移直接 FAIL。
- 标签背景可以使用低强调交互色或主题表面色，但不得默认复用按钮渐变。普通标签须单独登记 `labelSurface / labelText`，不能套用 Icon 底托的最弱显著性：忽略文字时底板仍应在 1:1 下与卡片可辨；承载有效信息的文字从 `80%` 有效强度起验证，交互/选中标签使用 `100%`，只有明确弱提示且真实清楚时才可降到 `60%`，不得使用 `40%` 弱化档。媒体封面内 `protected-media-overlay` 标签继续精确保留。
- 一级 Tab、二级 Tab、标签和按钮必须分开识别。
- 一级 Tab 选中态使用弱于邻近主要操作的纯色方向，禁止材质化大渐变；选中态必须一眼可辨。
- 现有结构支持时，选中/未选中优先形成两类可感知差异；只有一个既有状态载体时允许一类明确、稳定的状态信号，记录结构依据并在实际尺寸验证，不为凑数量新增几何。普通正文同 RGB 的轻微 Alpha 差不能作为唯一信号。
- 二级 Tab 可以更弱，但仍须有清楚的选中信号。选中 Tab 文字默认 `100%` 有效强度，未选 Tab 文字从 `80%` 起验证；不能仅靠极淡文字和极淡底板同时弱化状态。
- 若状态由 Variant、组件属性或内部可见性控制，保留当前状态，不凭名称猜测。
- `protected-media-overlay` 完全保留原色；保护必须精确到封面内覆盖节点，不能按“视频组件祖先”跳过整个子树。
- `protected-rank-top3` 的前三名名次文字、徽章/奖牌、底托/领奖台及其形状装饰完全保留原 UI 颜色，详细范围以《Figma 执行规范》第 3.1 节的原稿清单为准。这些元素不套用新文字色、图标色、渐变或材质方案；其原色不属于待清理的旧主题残留。姓名、收益和其他未受保护内容继续按各自角色换肤，不能把前三名组件或整个排行榜整体排除。

## 10. 深色方向性描边

只有 `light-to-dark` 且存在明确受光证据时，允许给复合/重点卡最外层稳定表面和功能 Icon 容器新增或转换一条 `1px INSIDE` 极淡方向性渐变描边。`dark-to-dark` 只能重着色原有描边；无描边节点继续无描边。

受光侧 Alpha 通常约卡片 `8%–14%`、Icon 容器 `12%–20%`，随后渐隐至 `0`；这些是观察范围，不是机械固定值。重复普通卡优先重着色已有弱描边，禁止给内部异形叠层重复描边或给所有角色套同一条白框。

## 11. Phase 3 完成条件

将结果写入 `themeDecision`，至少包含：

```text
kvAnalysis
targetSalienceOrder / roleLightnessPlan / targetLuminanceTopology
paletteCandidates / candidateCountReason（按不确定性生成的完整方案）
chosenPalette / roleDecisionReasons / rejectedCandidates
schemeAnchorContract: background / card / number / icon / button / tab
accentFamilyPlan: number / icon / button 的稳定主体家族、iconSource=surface-environment、darkNumberSync=icon、来源与显著面积；浅色 UI 第三家族例外证据
surfacePalette / cardAtmospherePalette / surfaceFamilyPlan（角色→KV 锚点及表面家族，含 hueRelationshipPlan）
colorClarityPlan
colorClarityPlan.hsbGuardrails / darkUiSmallButtonSummary / darkUiLargeButtonSummary / lightUiSmallButtonSummary / lightUiLargeButtonSummary / iconSummary
schemeAnchorConformancePlan（六色 anchorId、精确目标 RGB、代表试色后读回与最终读回）
disabledButtonOpacityOverrides / labelRecipe（存在对应角色时）
controlColorSalienceOrder: icon-container < selected-tab < primary-button
textBaseColor / textRamp / textRampOverrides / textBaseColorOverrides
textTonePlan: targetUiMode / textBaseHsb / primaryEffectiveStrength / primaryHostClasses / overrides
titleAccent / dataAccent / iconRecipe / tabRecipe
smallButtonRecipe / ctaRecipe / buttonTextCandidates
buttonCompositeReview（Phase 3 检查计划，Phase 5 填入真实试色结论）
cardAtmosphereReview / representativeCoverage（叠层职责、模式转换与全量材质覆盖）
representativeNodeRoles
preflightThemeDecision=pass
```

缺少任何现有角色、显著性顺序、有依据的完整方案评估及必要比较、六色 `schemeAnchorContract`、六个锚点的精确 `anchorId` 目标、按钮文字组合、逐角色 Paint Recipe 或背景/卡片/主要操作的色相关系计划时，Phase 3 不得通过。无金属撞色必须记录可靠 `surfaceContrastBasis`、对向候选与 KV 鲜明候选的比较、`contrastDerivation=hue-opposition|kv-vivid-accent` 以及可见色相分离；有可靠金属证据时必须记录 `metalAccentEvidence`，并在用户未限制方向时完整提供 `metallic-analogous / gold-bright / clean-deep` 三案。正常明亮金色若暗沉、偏铜棕、只靠高光呈金色，或未以深棕字作为默认文字方向验证，即 FAIL。功能 Icon 图形未引用或有依据地派生自 `icon`、主要小按钮与 CTA 未共同引用 `button`、Tab 未精确引用 `tab`，或真实合成后未满足 `icon-container < selected-tab < primary-button` 且无预先登记的业务例外时同样不得通过。候选仅一套且依据充分不算缺少比较，但不能据此绕过金属三案契约。
