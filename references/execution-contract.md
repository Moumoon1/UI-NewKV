# 执行契约

仅执行 Figma 换肤时于 Phase 0 完整读取；分析或维护 Skill 不因此启动设计写入。本文件统一维护执行次数、恢复、修复及证据约束，颜色定义仍以《颜色决策规则》为准，功能入口检查另见[《功能入口保真》](interaction-entry-contract.md)。

## 默认单次执行契约

用户确认配色后，普通换肤固定采用 **一次完整原稿基线读取、可回收的写前真实预览、一次正式批量写入、一次最终审查**。预览不交付、不留下设计节点；每个冻结交付/修复事务仅执行一次批量写入与一次集中终审，同方案内的修复按下节处理。这是调用与证据边界，不是建议：

`preflight_full.py` 的顺序为：先 `--stage static`，仅在返回 `ready-for-preview` 时启动可回收预演；原生截图落盘、真实宿主采样完成后再 `--stage full`，取得 `pass` 并独立审查 1:1 图。静态阶段不声称完整通过，正式写入不能早于完整阶段与视觉审查。
预演后若有大量文字宿主关系，先用 `scripts/prepare_contrast_sample_queue.py` 从冻结原稿、目标投影、`textRangePlan` 与规则账本列出逐区间取样队列。它仅为可确定的 SOLID Paint 和不透明单层宿主提供属性候选；有精确 Alpha 路径的纯色文字可在该宿主上形成合成候选。所有行仍是 `needs-review`；渐变、多 Paint、复杂 Alpha、位图遮挡和真实字形/宿主必须对照原生 1:1 截图人工确认，再形成 `contrastSamples.json`。候选数量或属性比值不能冒充 `--stage full` PASS。
冻结规则时就要让 `contrast-baseline.verifier.policy/decisionContext` 与 `manifest.themeTransition` 一致：深浅跨模式必须为 `contextual` 且写明真实模式与原因；同模式纯换色不得借 contextual 跳过来源对比。此校验在静态阶段再执行一次，不能等预演后才发现策略错配。

超过 100 个有效通道的页面，工作台默认使用 `--max-unit-channels 25 --merge-channel-kinds` 生成第一份审查队列；同时保留父级材质/状态的整体复核。跨 Paint、文字区间、描边、渐变、矢量镜像的同旧色候选必须分别确认视觉职责一致，否则拆成更窄规则。固定深度只用于补看父级或更细的上下文。这些选项只调整审查颗粒度，不减少待审路径、不自动赋色。

1. `Phase 1W` 只采集一次稳定的完整原稿快照，同时取得原稿整页图和必要的 1:1 原生局部图；后续角色分类、配方展开、节点映射、合成色计算、Icon/材质/状态关系检查和目标副本投影全部在本地完成。禁止为不同检查重新遍历或传输整棵原稿树。
   对复杂页面先用 `source_channel_triage.py` 审查区域，再用 `visual_unit_review_workbench.py` 将同一快照与原生整页图并排按视觉单元审查，最后用 `expand_channel_decisions.py` 将**人工确认**的节点/子树/颜色条件规则展开为逐路径草案。工作台同时输出按区域排列的 `review-queue.md`；按队列逐组看完整成员，确认后累计 `decisions.json` 并复跑展开器，直至剩余路径为零。展开器 `suggestedGroups` 中跨场景的大旧 RGB 组只用于发现重复色，**不是停点，也不得直接整组套色**；拆成工作台的场景/单元组及必要逐路径例外继续审。必须查看每条广域规则的完整命中路径并冻结 `reviewedPathsHash`，逐路径例外需显式覆盖原规则。工作台候选分组没有角色/目标色，坐标只是定位辅助；同一个旧 RGB 下不同按钮、数据、标题不可合并判断。`ready-for-semantic-review` 仅表示通道计划没有漏项/冲突，不表示语义、标题/Icon、文字宿主或视觉门禁通过；`needs-review` 时不得进入静态预检。通道数量大本身不构成阻塞；只有原生图/节点证据缺失、精确匹配无法判定、或规则冲突无法消解才如实停下。详见《局部试色与执行工具》Phase 1W。
2. 写入前必须从该快照生成完整 `colorManifest`、`iconGlyphPlan`、`materialRelationPlan`、表面/容器合成关系和状态组强弱关系；用投影后的目标快照在本地跑完确定性门禁。Icon 图形存在的每个可见 Vector/Boolean/Stroke/Effect/渐变色标都须有处理结论；浅色容器按最终 Alpha 合成色验证；同一状态组内原稿存在的非等强关系须自动完整展开为 `emphasisOrders`，不得人工只挑一个代表。
   对新 KV 替换旧 Hero，逐个列出与 Hero 可见区域相交的原 IMAGE/旧 KV 载体，比较它们的真实边界、祖先裁切和新 KV 实际覆盖范围；只要旧图可能从新 KV 下方或侧边露出，就必须给精确节点规划 `remove-visually`（如节点 opacity 归零）或证明被完整遮挡。不得因为新 KV 已放在顶层、原图局部被盖住而默认旧图消失。大面积 Vector/Boolean 底板按几何覆盖和最终可见面积判为卡片/内层容器，不因它与头像、图标相邻就归入装饰支撑色。每张卡顶还要区分越过标题栏的装饰蒙版残色与原稿本就存在的子标题底板；前者需消除突兀裁切，后者保留结构并按新模式重着色。
   **执行门槛：** `coverage=pass` 只证明通道已列全，不证明角色正确、计划可写或视觉合格。写前必须运行 `scripts/preflight_full.py` 汇总实际机器审计，并单独审查真实尺寸预览；其中 `visible-surface-roles` 会拦截大面积、实际可见的非文字 Fill 承载层误用文字/细节配方（含实色次级细节），尤其是 Vector 卡片底板和标题带；它不能代替逐卡目视检查。该脚本还会调用 `preflight_instance_writes.py`、`derive_vector_mirrors.py`、完整投影、Icon/文字/材质/跨模式/对比度/视觉单元等独立检查。任何 `failedChecks`、缺失输入、手填 `pass` 或预览失败均不能进入写入。实例中的 `vectorNetwork/vectorPaths` 不可直接设值；需要改它们时先规划所有相关实例的解绑与解绑后映射，或逐路径证明与同节点可写 Fill/Stroke 的来源色和目标色相同，并在预演/终审做目标读回。若原生预演出现“文字区间读回为目标色、单层导出正确，但整页仍显示旧色”，必须把受影响文字的实例祖先加入冻结 `detachInstanceIds`，从外到内解绑后重跑完整预演，并按结构指纹校验；不得靠重复设置颜色或切换透明度假装修复。空 `boundVariables` 键不是有效绑定，全部目标为保留且无有效绑定的 setter 必须从写集删除。
3. 跨模式或复杂材质任务在正式写入前，用 `scripts/generate_figma_staged_preview_js.py` 对**同一冻结写入函数**做可回收预演：先核对原稿指纹、创建带唯一标记的临时副本并应用整套计划；随后用 Figma 截图接口取得它的 1:1 整页图；最后在编排层的 `finally` 中按精确 ID 清理，并核对页面子节点和原稿指纹未变。预演应用失败须在同一调用清理；截图或外部调用失败也必须进入精确清理步骤。清理失败立即停止，绝不能交付。预演不是代表试色或部分写入，不能只预演一张卡。正式写入前须核对逐操作回执、目标投影指纹、全页视觉及预登记细节；计划一旦改变，原预演失效。
4. 唯一一次**正式** Figma 写入调用在开始时核对原稿指纹与已通过预演的计划指纹，然后在同一程序内完成 clone、KV 放置、必要解绑、全部颜色叶子修改和精确回执。技术分块只能发生在该调用内部；不得先写代表、再逐卡扩展，也不得在写入过程中反复获取整树或截图试错。
5. 正式写后只进行一次集中终审阶段，使用两条已验证的证据通道：`generate_figma_final_review_js.py` 返回原稿不变指纹和无损 `KVSS1` 完整副本快照，Figma 截图接口再取同一副本的 1:1 整页 PNG。两个文件都必须真实落盘并校验，局部图从整页图本地裁取；源稿图复用 Phase 1 证据。少一条通道即审查失败，不能从返回 JSON 的字节数推断证据已到达。若快照 image block 已返回但编排层未把二进制落盘，可有限次只读重取同一副本证据并如实记录，不得因此重写设计。Figma 可能把换成相同 Paint 的相邻 styled text 区间合并；终审按原字符跨度逐段验证实际 Paint/Alpha，不以旧数组索引存在作为通过条件。节点几何只容许有明确渲染不变证据的极小 API 浮点漂移，不能把可见位移归入容差。所有灰度、模糊、缩略图和机器审计在本地派生。若终审失败，保留失败证据，按执行工具的有界修复契约继续推进；不得盲目进入“再读整树—再写一轮”的循环。

可回收完整预演属于上述默认契约，不是交互式现场试色。只有用户明确要求交互式现场试色，或正式单次调用在**任何持久设计变更发生前**因平台硬限制失败，才可偏离该契约；偏离原因、是否发生部分写入和新的调用上限须先明确记录。代表试色、逐区写入及每批现场扩展仅适用于这一显式例外模式。终审失败后的有界修复不属于现场试色，也不要求用户重复授权。

## 强制执行协议

规则分层：原稿、业务结构、字体/文案、精确保护、写入白名单、真实证据及本次基础交互与背景备选覆盖/确认门禁是硬边界；文字 Alpha 档位及默认位置是可解释调整的起点。新 UI 必须在实际尺寸下可读、状态可辨、容器边界可辨；仅深→深、浅→浅且不涉及画风迁移的普通换肤，要求每个对应关系的最终合成对比度不得低于原 UI；深浅转换或画风迁移按新 KV、实际宿主、材质与业务层级确定目标，原稿比值作参考，不作为逐点硬门槛。任何模式都不能用文字通过替代底色或状态通过，可读性、操作突出、状态和边界可辨均必验。此要求优先于仅换 H、保留 S/V 的初始策略；必要时联合调整合法的背景与前景，仍保持 KV 家族、明快感和保护结构。基线建立、采样与严格比较统一按《验收规则》第 5.1 节。WCAG 固定比值仍不默认启用；用户另有明确标准时同时执行，不以追求最高比值代替审美与角色层级。

首次执行按 `Phase 0 → Phase 1P → Phase 2 → 用户选色 → Phase 1W → Phase 3 → Phase 4/5（本地计划、可回收整页预演与预检）→ Phase 6（单次正式批量写入）→ Phase 7（单次终审）` 推进。实际工作主线为：一次完整基线读取与分类 → 统一家族配方 → 本地投影全部目标 → 可回收原生预演 → 一次正式写完整页 → 一次集中终审。阶段表示证据依赖，不授权代表试色或逐卡写入。

多图层控件按完整视觉单元换肤。Phase 1 从真实承载层建立 `sourceAudit.visualUnits`，Phase 3 冻结成员、同色关系、对比关系与可比较的强弱顺序；配方按整组推导。局部修正继承同一登记表与规则，通过工具计算受影响关系闭包并使门禁失效，不能只验本次改色的节点。登记、完整上下文复验及工具格式只维护在[执行工具第 4.8 节](execution-workflow.md#48-视觉单元与局部修正闭包)。

- 每个 Phase 的“必须产出”和“通过条件”全部满足后，才允许进入下一阶段。
- 配色方案确认是输入充分时正式 UI 写入前唯一例行业务决策点；确认前只做只读分析与方案展示，不复制页面、不替换 KV、不写 UI。方案确认后的职责分类、合法语义拆色、次级入口配方及范围内修复自主推进，不询问“拆不拆”或因清单规模终止任务。静态计划离线完成；跨模式/复杂材质增加可回收整页预演，但不做代表性试色或无新证据的盲目写入循环。这**不覆盖** Codex/Figma 的工具权限审批，也不授权绕过审批或扩大访问范围。
- 正式写入前的阶段失败必须在本地计划中修正并重新投影，重做可回收预演；Phase 7 真实终审失败记录未完成，并在已确认方案和原授权范围内按影响闭包继续有界修复，不等待用户重复授权。不得以时间或页面复杂为理由省略检查。
- 离线投影范围、单次写入回执和终审失败处理统一按[《局部试色与执行工具》](execution-workflow.md)执行；不能反复读取整树、现场盲试或沿用过期 PASS。
- 目标/KV 不唯一或不可访问、文件无法解码、权限不足、必要写入/证据路径确实不可用，或允许例外仍无法避免破坏保护结构时，才可说明真实阻塞并请求所缺信息/授权。先完成安全核查与有依据的恢复路径；局部阻塞不停止无依赖的工作。比例差异、原稿普通文字低 Alpha、可选字体加载失败不是停止理由，文字恢复见《文字换色与恢复》。
- 不得在没有实际读取、写入或截图证据时声称已经执行、检查或通过。无法取得证据的项目按 `FAIL` 处理。
- Phase 1W 优先用 `scripts/generate_figma_baseline_js.py <sourceFrameId>` 生成一次完整采集、绑定风险汇总和无损快照导出的 `use_figma` 程序；用 `scripts/decode_theme_snapshot_png.py` 校验并落地返回的二进制产物。不得在正式任务中临时测试多种传输通道。产物缺失或校验失败时，仅在能保证同一次稳定采集的前提下切换到《局部试色与执行工具》第 5.4 节的分片后备路径；否则报告传输阻塞，不反复尝试同一失败方案。
- `use_figma` 返回完整基线后，编排代码的**第一步**必须把 `image/png` block 的完整 `data` 放入持久 `store`，随后在同一执行链按第 5.4 节分块送解码器并核对本地文件；只输出 `dataLength` 摘要会在执行单元退出时永久丢失唯一快照，不能再为弥补该遗漏重采原稿。该步骤使用第 5.4 节的具体编排范例，不凭记忆重写。
- Phase 3 先估计节点、颜色通道、变量/样式绑定和全部写入操作。副本交付采用**固定颜色**：解绑计划、有效显示色、目标 Paint 和节点映射都从原稿快照在本地投影；唯一写入调用在副本内按“clone/KV/必要解绑/颜色叶子”顺序执行并逐原子核对 setter 结果，明确排除 `kvLockedSubtreeRootIds`。不能先写一部分再读取决定下一部分。
- Phase 3 在完整语义 `colorManifest` 审核后，用 `scripts/compile_color_mutation_plan.py` 从本轮原稿/KV 快照、冻结目标色和**显式** Alpha/解绑例外生成 `writePlan`、`expectedClone`、`policy`、`nodeMap`；编译器不选择角色/色值或捏造例外，生成后仍须补齐规则、视觉单元与关系证据并运行 `preflight_full.py --stage static`。不再为每个页面重写任务专用 builder；若编译器拒绝不支持的 Effect/Alpha 写法，不能手填 PASS 绕过。
- Phase 3 的非颜色证据先可用 `generate_visual_unit_declarations.py` 从同源工作台列出**未审**单元根模板，再人工补 basis/依赖/视觉规则；之后用 `compile_visual_unit_registry.py`（审核过的完整单元根→全部存储通道的唯一归属）、`prepare_semantic_preflight.py`（显式 Icon/保护/禁用/接缝根→Icon、文字区间、跨模式义务）和 `freeze_rule_ledger.py`（人工填写适用性/范围/验收条件后冻结账本及 manifest hash）编排。模板不能直接编译通过；这些工具只把人工证据精确展开，不产生原生视觉 PASS。依赖和格式见《局部试色与执行工具》的“审核计划编排工具”。仍须运行 `preflight_full.py --stage static` 得到真实 `ready-for-preview`，再可回收预演。
- Phase 3 按组件家族、材质、状态与宿主类别统一制定配方，登记全部实例和确切区域归属；同族等价实例复用配方，非等价项在本地目标投影中分别验证。Phase 5 先离线静态检查，再以可回收副本做真实整页预演并清理；Phase 6 是唯一正式批量写入；Phase 7 一次取得全部最终证据并集中审查。
- Phase 7 在集中终审中传完整副本快照并同时验证原稿指纹。`color-bindings-clear` 必须在最终 UI 范围快照上为 PASS；新 KV 锁定子树须排除根节点插入位置和锁定状态后与原 KV 全部属性一致。最终真实截图还须与已通过的同一冻结写入计划预演做逐像素核验；相邻同色文字区间按字符覆盖核验，不能因 Figma 合并区间误报，也不能因合并跳过任何字符。不能只凭 RGB、截图或 Selection Colors 判定。
- 把性能与审批作为可观察结果：分别记录完整基线读取、每次可回收预演、正式写入和终审的墙上耗时、字节数、清理结果与实际审批原因；拿不到审批详情记 `unknown`，不得写 0。默认不调整用户权限模式，也不把内部数组分块算成多次设计写入。
- 在 `Phase 5` 的静态及可回收真实预演全量预检通过前，禁止执行唯一正式写入；在 `Phase 7` 通过前，禁止报告“换肤完成”。
- 写前预检须从原稿与投影逐关系生成可复验结果，不能把方案六色的静态对比度、通道计数或自写 JSON `status=pass` 当成全页预检。对页面↔卡片↔内部容器、KV 接缝、普通/禁用按钮字、媒体状态标签和同族控件，在实际尺寸预览中逐项检查；缺真实背景或预览时保持未通过。

按时间顺序维护 `executionPhaseLog`。最低顺序为：

```text
inspect-fast → kv-style-check → kv-analysis → palette-proposal
→ palette-selected(user) → source-audit-full(one-read)
→ offline-plan → static-preflight → disposable-full-preview(cleaned)
→ full-preflight(pass) → single-committed-batch-write → final-review(one) → audit(pass)
```

## 有界修复与无进展处理

本节是同方案修复的唯一次数/授权定义，其他参考中的“一次/唯一”均指每个冻结事务。用户已要求完成换肤或修正反馈时，已选方案和原授权持续有效。首轮失败保留证据并继续诊断，不把审计失败变成新的确认问题。

上一轮已按约定清理证据时，新建 runWorkspace，允许为继续反馈重建一次当前原稿基线并核对身份/指纹；这不是反复为不同门禁重采，也不重提已选方案。已有副本继续使用，不去其他历史目录猜测输入。

修复前必须：核对原稿/KV 身份与保护指纹；以当前副本新鲜证据定位失败及已成功操作；冻结精确修复路径、真实 before/after、原因和依赖闭包；保持布局/保护/已选锚点。旧 before 与现场值不符时先查明原因，禁止把未知外部修改静默纳入允许集合。每轮修复重新投影和预演，在现有副本内一次批量应用并集中终审，不重复 clone，不重放已成功的整批操作。相关旧 PASS 失效，未变化基线和规则复用。

同一失败没有新增诊断证据或合法调整时，停止重复写入，继续只读定位和独立工作；不能无限重复同一错误。只有对象/资产不唯一、权限或证据不可得、需要改变方案/范围/保护约束，或已证实没有可执行合法路径时，才报告真实阻塞并请求所缺输入。调用数与修复事务分别如实记入 mutationPlan，禁止事后把多轮记成一次。
